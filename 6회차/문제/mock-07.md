## 문제 7

### 문제

온라인 경매 시스템에서 `경매체결` 테이블(약 4,000만 건, 블록당 약 100행 → 약 40만 블록)을 특정 물품카테고리 조건으로 조회한다. 카테고리 컬럼의 인덱스 `경매체결_N1`로 20만 건을 뽑는데, 인덱스를 타는데도 25초가 걸린다. 아래 TKPROF에서 지연의 원인을 직접 지목한 것으로 옳은 것은?

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.004         0.004        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch        401     3.000        24.996    40000    191400         0    200000
--------------------------------------------------------------------------------
Total        403     3.004        25.000    40000    191400         0    200000

Rows       Row Source Operation
--------------------------------------------------------------------------------
 200000     TABLE ACCESS BY INDEX ROWID 경매체결 (cr=191400 pr=40000 pw=0 time=24500000 us)
 200000      INDEX RANGE SCAN 경매체결_N1 (cr=1400 pr=200 pw=0 time=350000 us)
```

### 선택지

① 테이블 액세스 자체 블록 I/O 190,000이 액세스 ROWID 수 200,000과 거의 같아 클러스터링 팩터가 최악이다. 이 190,000이 전체 cr의 99.3%와 time 24.5초를 차지하고 40만 블록 테이블의 47.5%를 단일 블록 랜덤 읽기로 훑어 손익분기점을 넘었으므로, 커버링 인덱스로 테이블 액세스를 제거하는 것이 답이다.

② 병목은 INDEX RANGE SCAN이다. 이 인덱스가 20만 건을 걸러내며 cr 1,400·pr 200을 쓰는데, 20만 개의 ROWID를 뽑느라 리프 블록이 조각나 time=0.35초가 붙은 것이다. 인덱스를 리빌드해 리프를 조밀하게 만들면 ROWID가 정렬돼 상위 테이블 액세스의 24.5초까지 함께 정리되므로 25초 응답이 1초대로 줄어든다.

③ Fetch 401회는 20만 행을 클라이언트로 실어 나른 왕복이고, 왕복 한 번에 24.5초/401 ≈ 61밀리초의 지연이 붙어 24.5초가 쌓였다. 배열 인출 크기를 지금의 500행에서 5,000행으로 키워 Fetch를 41회로 줄이면 왕복 지연이 1/10이 되어 테이블 액세스 지연도 함께 사라진다.

④ 물리 읽기 Disk 40,000이 time=24.5초의 근본 원인이다. 40,000블록을 단일 블록으로 읽으며 회당 약 0.6밀리초씩 24초가 쌓인 것이므로, 버퍼 캐시를 키워 이 40,000을 논리 읽기로 돌리면 cr 191,400만 남아 응답이 최적화되고 인덱스 구성은 손댈 필요가 없다.

---

### 정답 — ①

### 왜 ①인가

Row Source의 cr는 **누적**이므로, 테이블 액세스 노드의 191,400에서 자식 인덱스 1,400을 빼면 **테이블 자체 블록 I/O**가 나옵니다. 이를 ROWID 수로 나눠 **클러스터링 팩터**를 가늠합니다.

```text
테이블 자체 블록 I/O = 191,400 − 1,400 = 190,000
액세스 ROWID(행) 수  = 200,000
CF 추정 = 190,000 / 200,000 ≈ 0.95 블록/행
  → 행마다 거의 다른 블록 → 클러스터링 팩터 최악(≈ 행 수에 근접)
```

CF가 나쁘면 인덱스로 뽑은 각 행이 서로 다른 테이블 블록에 흩어져 있어, **테이블 Random 액세스**가 한 행당 블록 하나씩을 단일 블록으로 읽습니다. 어디에 시간이 쏠렸는지 봅니다.

```text
테이블 액세스 cr 비중 = 190,000 / 191,400 × 100 ≈ 99.3%   ← 논리 읽기의 대부분
인덱스 스캔 cr 비중   =   1,400 / 191,400 × 100 ≈ 0.7%    ← 극소
테이블 액세스 time    = 24.5초 (인덱스 스캔 time은 0.35초)
```

이제 **손익분기점**입니다. 테이블은 약 40만 블록인데, 인덱스 경유로 읽는 테이블 블록이 190,000입니다.

```text
인덱스 경유 테이블 블록 = 190,000
테이블 총 블록          = 40,000,000 / 100 = 400,000
비율 = 190,000 / 400,000 = 47.5%
  → 테이블의 절반 가까이를 '단일 블록 랜덤 읽기'라는 느린 경로로 훑음
  → 다중 블록 Full Scan 손익분기점을 이미 넘음
```

인덱스 스캔(cr 1,400·0.35초)은 문제가 아닙니다. 정체는 **CF 최악으로 부풀어 오른 테이블 Random 액세스 190,000블록**이며, 이는 필요한 컬럼을 인덱스에 더한 **커버링 인덱스**로 테이블 액세스 자체를 없애거나 Full Scan으로 전환할 때 사라집니다. 따라서 ①이 원인을 정확히 지목했습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | 테이블 자체 cr 190,000(=191,400−1,400)이 ROWID 200,000과 거의 같아 CF≈0.95로 최악이고, 이 190,000이 cr의 99.3%·24.5초를 차지하며 40만 블록의 47.5%를 랜덤 읽기로 훑어 손익분기점을 넘었다는 지목과 커버링 인덱스 처방이 정확합니다 |
| ② | ✗ | cr 1,400·pr 200·time 0.35초는 맞지만, 그 값이 곧 INDEX RANGE SCAN이 병목이 아니라는 증거입니다(cr의 0.7%). 리빌드는 리프를 조밀하게 만들 뿐 테이블 블록의 물리적 배치(CF)를 바꾸지 못하므로, 190,000블록의 테이블 Random 액세스는 그대로 남습니다 |
| ③ | ✗ | Fetch 401회는 배열 크기 500(=200,000/400)의 결과일 뿐입니다. 24.5초를 401로 나눠 61밀리초를 왕복 지연이라 부른 것은 순환 논증이고, 그 24.5초는 Row Source가 테이블 액세스 노드에 붙여 놓은 시간입니다. Fetch를 41회로 줄여도 읽어야 할 190,000블록은 그대로입니다 |
| ④ | ✗ | Disk 40,000이 24초를 만들었다면 0.6밀리초라는 계산은 성립하지만, 40,000을 전부 캐시 적중으로 돌려도 테이블 자체 논리 읽기 190,000블록(단일 블록 랜덤)은 남습니다. 병목은 물리 읽기가 아니라 CF가 만든 논리 블록 액세스 횟수이므로 버퍼 캐시로 오귀속한 것입니다 |

## ✅ 이 문제의 핵심

1. **Row Source cr는 누적입니다.** 테이블 자체 블록 I/O = 상위(191,400) − 자식 인덱스(1,400) = 190,000. 이걸 ROWID 수로 나눠 CF를 가늠합니다(190,000/200,000 ≈ 0.95 블록/행).
2. **CF가 최악이면 테이블 Random 액세스가 병목**입니다. 190,000이 cr의 99.3%·time 24.5초를 차지하고, 인덱스 스캔(1,400·0.35초)은 무죄입니다.
3. **손익분기점**: 인덱스 경유 테이블 블록 190,000이 총 40만 블록의 47.5%를 단일 블록 랜덤으로 훑으면 다중 블록 Full Scan보다 불리합니다.
4. 처방은 인덱스 리빌드·배열 크기·버퍼 캐시가 아니라 **테이블 액세스 자체 제거**(커버링 인덱스) 또는 Full Scan 전환입니다.

📌 한 줄 정리: 테이블 자체 cr 190,000이 ROWID 200,000과 거의 같아 CF가 최악이고, 이 190,000블록의 랜덤 액세스가 cr의 99.3%·24.5초를 차지하며 손익분기점을 넘었으므로 처방은 인덱스·캐시가 아니라 커버링 인덱스로 테이블 액세스를 없애는 것입니다.
