## 문제 3

### 문제

모바일 뱅킹 푸시 알림 발송 배치가 발송 대상자 80만 명을 순회하며 대상자 1명당 알림 1건씩(총 80만 건)을 `알림발송내역`에 적재한다. SQL 텍스트는 하나로 고정하고 조건값은 모두 **바인드 변수**로 넘기는데, 발송 함수가 반복문 안에서 커서를 매 회 새로 열고 닫는 구조라 실행마다 Parse 콜이 한 번씩 나간다. 8개의 발송 세션이 동시에 돌자 응답이 64초로 늘고 대기 이벤트 상위에 `library cache: mutex`(라이브러리 캐시) 경합이 잡혔다. 아래는 이 배치 세션의 비재귀·재귀 statement를 나눠 집계한 TKPROF이다. 지연의 원인을 직접 지목한 것으로 옳은 것은?

(단, 옵티마이저 통계는 최신이고 SQL 텍스트는 대소문자·공백까지 동일해 라이브러리 캐시에서 공유되며, Shared Pool은 여유가 충분해 에이징으로 인한 강제 재파싱은 없다.)

#### [아 래]

```text
OVERALL TOTALS FOR ALL NON-RECURSIVE STATEMENTS

Call       Count   CPU Time  Elapsed    Disk    Query  Current    Rows
----------------------------------------------------------------------
Parse     800000     20.000    55.000       0        0        0       0
Execute   800000      8.000     9.000       0  1600000   900000  800000
Fetch          0      0.000     0.000       0        0        0       0
----------------------------------------------------------------------
Total    1600000     28.000    64.000       0  1600000   900000  800000

Misses in library cache during parse: 12


OVERALL TOTALS FOR ALL RECURSIVE STATEMENTS

Call       Count   CPU Time  Elapsed    Disk    Query  Current    Rows
----------------------------------------------------------------------
Parse         20      0.010     0.010       0        0        0       0
Execute       40      0.020     0.020       0      120        0       0
Fetch         60      0.010     0.010       0      180        0      40
----------------------------------------------------------------------
Total        120      0.040     0.040       0      300        0      40

Misses in library cache during parse: 8
```

### 선택지

① 비재귀 Parse가 CPU 20.0초로 Total CPU 28.0초의 대부분을 차지하고 라이브러리 캐시 미스도 비재귀 12건·재귀 8건이 잡혔으니, 병목은 계획을 새로 만드는 하드파싱이다. `cursor_sharing=FORCE`로 하드파싱을 소프트파싱으로 돌리면 라이브러리 캐시 경합과 Parse elapsed 55.0초가 함께 줄어든다.

② 비재귀 User Call이 Parse 80만 + Execute 80만 = 160만 콜이고 Fetch는 0이라, 64.0초를 160만으로 나누면 콜당 40마이크로초로 정체는 클라이언트–서버 왕복 자체에 있다. 8개 세션이 동시에 던지는 이 왕복을 배열 처리와 커넥션 풀링으로 줄이면 Parse elapsed 55.0초의 대기가 해소된다.

③ 라이브러리 캐시 미스는 12건뿐이라 하드파싱은 사실상 없고, 병목은 Parse 콜 80만 건(Parse:Execute = 1:1)이 라이브러리 캐시 mutex를 다투는 소프트파싱 폭주다. 커서를 한 번만 파싱해 반복 실행(`session_cached_cursors`·홀드 커서)하도록 바꿔 Parse 콜을 줄이면 64초가 해소된다.

④ Execute가 Query 1,600,000·Current 900,000으로 합계 250만 블록을 만지며 80만 행을 적재해 행당 3블록이 넘고, 8개 세션이 이 논리 읽기를 동시에 일으켜 버퍼 캐시 경합을 만든 것이 64초의 골격이다. DB 버퍼 캐시를 키워 이 논리 읽기를 줄이면 Parse 단계의 대기도 함께 사라진다.

---

### 정답 — ③

### 왜 ③인가

SQL 텍스트가 하나로 고정돼 있고 바인드 변수를 쓰므로, 커서는 라이브러리 캐시에서 **공유**됩니다. 그래서 파싱은 대부분 **소프트파싱**입니다. 먼저 **하드파싱율**을 셉니다.

```text
하드파싱율 = 라이브러리 캐시 미스(비재귀) ÷ 비재귀 Parse 콜
          = 12 ÷ 800,000 ≈ 0.0015%
  → 하드파싱은 사실상 없음(계획을 새로 만든 건 12회뿐)
```

재귀 statement도 Parse 20·Execute 40으로 미미합니다. 하드파싱이 데이터 딕셔너리를 뒤지는 재귀 폭주가 없다는 뜻이니, 계획 생성 축은 병목이 아닙니다. 그런데 응답은 64초입니다. **파싱 콜 횟수**와 **파싱 대기**를 봅니다.

```text
Parse 콜 : Execute 콜 = 800,000 : 800,000 = 1 : 1   → 커서 미보유, 실행마다 재파싱
Parse elapsed − Parse CPU = 55.0 − 20.0 = 35.0초    ← 라이브러리 캐시 대기(mutex)
Parse elapsed 비중 = 55.0 ÷ 64.0 × 100 ≈ 85.9%
실작업(Execute) elapsed = 9.0초 (전체의 14.1%)
```

Parse에 55초가 잡혔는데 그중 35초가 CPU가 아니라 **대기**입니다. 하드파싱이 12회뿐인데도 대기가 큰 이유는, 소프트파싱도 라이브러리 캐시에서 커서를 찾느라 mutex를 잡기 때문입니다. 여기서 두 축을 분리해야 합니다.

```text
축 A: 하드파싱(계획 생성·라이브러리 캐시 MISS) ── 12건(0.0015%) → 병목 아님
축 B: 파싱 콜 횟수(소프트파싱·라이브러리 캐시 latch/mutex) ── 800,000건 → 35초 대기의 정체

동시 8세션이 매 실행마다 Parse 콜을 던지면, 하드파싱이 0에 가까워도
소프트파싱끼리 같은 커서의 mutex를 서로 다퉈 축 B가 독립적으로 병목이 된다.
```

처방은 커서를 한 번만 파싱해 반복 실행하도록(홀드 커서·`session_cached_cursors`) 바꿔 **Parse 콜 자체를 없애는 것**입니다. Parse 콜이 줄면 라이브러리 캐시 mutex 경합도 함께 사라집니다. ③이 하드파싱 축(계획 생성)과 파싱 콜 축(소프트파싱 빈도)을 옳게 분리했습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | Parse CPU 20.0초와 미스 12·8건을 하드파싱 비용으로 본 것이 오류입니다. 비재귀 미스 12건은 Parse 콜 80만의 0.0015%뿐이라 계획 생성은 사실상 없고, SQL은 이미 바인드 변수라 `cursor_sharing=FORCE`가 바꿀 리터럴도 없습니다. 파싱 콜 축을 하드파싱 축으로 오인한 별개 축 혼동입니다 |
| ② | ✗ | 콜 160만과 콜당 40마이크로초는 산술로는 맞지만, User Call 수는 파싱·실행 횟수일 뿐 왕복 지연이 병목이라는 뜻이 아닙니다. 이 배치는 INSERT라 Fetch가 0이고 대기는 Parse의 mutex(55.0−20.0=35초)에서 났으므로, 배열 처리·커넥션 풀링은 왕복 축을 겨냥할 뿐 파싱 콜 mutex를 줄이지 못합니다 |
| ③ | **○** | 하드파싱율 12/800,000 ≈ 0.0015%로 계획 생성 축은 무죄이고, Parse:Execute = 1:1의 소프트파싱 80만 콜이 라이브러리 캐시 mutex를 다퉈 Parse elapsed 55초 중 35초가 대기임을 짚어, 커서 홀드로 Parse 콜을 없애는 처방이 정확합니다 |
| ④ | ✗ | Query 1,600,000 + Current 900,000 = 250만 블록은 Disk 0의 논리 읽기라 이미 전부 메모리에서 처리됐고, Execute elapsed는 9.0초(14.1%)뿐입니다. 병목은 실행 I/O 축이 아니라 Parse의 mutex 대기 축이므로, 버퍼 캐시를 키워도 55초의 파싱 대기는 그대로입니다 |

---

## ✅ 이 문제의 핵심

1. **하드파싱율 = 라이브러리 캐시 미스 ÷ Parse 콜.** 여기서는 12/800,000 ≈ 0.0015%로, 바인드 변수 + 텍스트 고정이라 계획 생성(하드파싱)은 사실상 없습니다.
2. **하드파싱 축(계획 생성)과 파싱 콜 축(소프트파싱 빈도)은 별개**입니다. 하드파싱이 0에 가까워도 소프트파싱 콜이 많으면 라이브러리 캐시 mutex를 다퉈 독립적으로 병목이 됩니다.
3. **Parse:Execute = 1:1은 커서 미보유의 신호**입니다. 실행마다 Parse 콜이 나가 80만 회의 소프트파싱이 발생했고, Parse elapsed 55초 중 35초가 mutex 대기입니다.
4. 처방은 `cursor_sharing`·버퍼 캐시·커넥션 풀링이 아니라 **Parse 콜 제거**(커서 홀드·`session_cached_cursors`)입니다. 한 번 파싱해 반복 실행하면 mutex 경합이 사라집니다.
5. 축을 뒤섞으면 하드파싱 처방(①)·왕복 처방(②)·I/O 처방(④)으로 헛짚습니다.

📌 한 줄 정리: 하드파싱율이 0.0015%(12/800,000)로 계획 생성 축은 무죄인데도 64초가 걸린 것은 Parse:Execute = 1:1의 소프트파싱 80만 콜이 라이브러리 캐시 mutex를 다퉈(Parse elapsed 55초 중 35초 대기) 파싱 콜 축이 독립적으로 병목이기 때문이며, 처방은 커서를 홀드해 Parse 콜을 없애는 것이다.
