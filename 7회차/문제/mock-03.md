## 문제 3

### 문제

주차요금 정산 시스템의 야간 정산 배치가 주차권 40,000건을 순회하며 주차권마다 조건값을 문자열로 이어 붙인 리터럴 SQL 1건씩(총 40,000건, 서로 다른 SQL 문장)을 `주차정산내역`에 던진다. 8개의 배치 세션이 동시에 돌면서 응답이 72초로 늘고, CPU 사용률이 급등하며 대기 이벤트 상위에 `library cache: mutex`(라이브러리 캐시) 경합이 잡혔다. 아래는 이 배치 세션의 [비재귀 statements 합계]와 [재귀 statements 합계]를 나눠 집계한 TKPROF이다. 하드파싱과 재귀 파싱을 구분할 때, 다음 중 옳은 진단은?

(단, 옵티마이저 통계는 최신이고 바인드 변수는 전혀 쓰지 않았으며, Shared Pool 크기는 여유가 충분해 에이징으로 인한 강제 재파싱은 없다.)

#### [아 래]

```text
OVERALL TOTALS FOR ALL NON-RECURSIVE STATEMENTS

Call       Count   CPU Time  Elapsed    Disk    Query  Current    Rows
----------------------------------------------------------------------
Parse      40000     24.000    30.000       0        0        0       0
Execute    40000      4.000     5.000       0     2000        0       0
Fetch      40000      2.000     3.000     200   118000        0   40000
----------------------------------------------------------------------
Total     120000     30.000    38.000     200   120000        0   40000

Parse      50000      2.000     2.500       0        0        0       0
Execute   190000     16.000    18.000       0   700000        0       0
Fetch     240000     12.000    13.500     300   900000        0  190000
----------------------------------------------------------------------
Total     480000     30.000    34.000     300  1600000        0  190000

Misses in library cache during parse: 800
```

### 선택지

① 비재귀 Parse 40,000회 중 37,000회가 라이브러리 캐시 미스라 하드파싱율이 92.5%이고, 하드파싱이 부른 재귀 딕셔너리 조회까지 합치면 파싱이 전체 CPU의 90%다. 병목은 파싱 축이고 실행·계획·I/O 축과 독립이므로, 리터럴을 바인드 변수로 바꿔 소프트파싱으로 돌리면 라이브러리 캐시 경합과 72초가 함께 줄어든다.

② 비재귀 Parse 40,000회와 Execute 40,000회가 1:1로 맞물려 Total 120,000회가 되었으니 애플리케이션이 SQL 한 건마다 서버를 오간 것이고, 파싱 CPU 24.0초는 그 왕복 대기가 쌓인 결과다. 커넥션 풀링과 배열 인출 크기 상향으로 왕복 수를 줄이면 파싱 부하와 라이브러리 캐시 경합이 함께 해소된다.

③ 재귀 Execute 190,000회가 소비한 Query 700,000과 재귀 Fetch 240,000회의 Query 900,000을 합친 1,600,000 블록이 이 배치 논리 읽기의 대부분이므로, 병목은 재귀 SQL의 블록 소비다. DB 버퍼 캐시를 키워 이 1,600,000 블록을 캐시 적중으로 돌리면 파싱 시간과 라이브러리 캐시 경합이 함께 사라진다.

④ 재귀 파싱의 라이브러리 캐시 미스는 800회뿐이라 딕셔너리 커서는 잘 공유되고 있고, 하드파싱 37,000회는 매번 최신 통계로 계획을 새로 만들어 실행 품질을 높인다. 비재귀 Execute·Fetch CPU가 4.0 + 2.0 = 6.0초로 가벼운 것이 그 증거이니, bind peeking 위험을 떠안기보다 지금의 하드파싱을 유지하는 편이 안전하다.

### 정답 — ①

### 왜 ①인가

리터럴 SQL은 문장마다 텍스트가 달라 라이브러리 캐시에서 공유되지 못하므로, Parse마다 미스가 나 **하드파싱**이 됩니다. 먼저 **하드파싱율**을 셉니다.

```text
하드파싱율 = 라이브러리 캐시 미스(비재귀) ÷ 비재귀 Parse 수
          = 37,000 ÷ 40,000 = 92.5%
```

40,000번의 파싱 중 37,000번이 하드파싱입니다. 하드파싱은 계획을 새로 만들기 위해 데이터 딕셔너리를 뒤지는데, 이 딕셔너리 조회가 **재귀 statement**로 잡힙니다. 그래서 재귀 블록의 Execute·Fetch가 대량으로 발생합니다. 이제 **파싱 비중**을 봅니다.

```text
파싱에 든 CPU = 비재귀 Parse CPU + 재귀 전체 CPU(하드파싱이 부른 딕셔너리 조회)
            = 24.0 + 30.0 = 54.0초
전체 CPU     = 비재귀 30.0 + 재귀 30.0 = 60.0초
파싱 비중    = 54.0 ÷ 60.0 × 100 = 90.0%

실작업(비재귀 Execute+Fetch) CPU = 4.0 + 2.0 = 6.0초 (전체의 10%)
```

CPU 60초 중 54초(90%)가 파싱이고, 실제 주차정산내역을 읽고 나른 실작업은 6초(10%)뿐입니다. 응답 72초의 정체는 **파싱 축**에 있습니다.

```text
축 A: 파싱(하드파싱 37,000회) ── 라이브러리 캐시 경합·CPU 90%의 정체
축 B: 실행/계획/I/O           ── 실작업 CPU 6초로 이미 가벼움

동시 8세션이 저마다 하드파싱하면 라이브러리 캐시 mutex를 서로 다투므로,
파싱 축을 줄이지 않는 한 실행·I/O를 손대도 72초는 그대로.
```

처방은 리터럴을 **바인드 변수로 바꿔 하드파싱을 소프트파싱으로** 돌리는 것입니다. 같은 SQL을 공유하면 미스가 사라져 딕셔너리 재귀 조회도, 라이브러리 캐시 경합도 함께 빠집니다. ①이 파싱 축과 실행/계획/I/O 축을 옳게 분리했습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | 하드파싱율 37,000/40,000 = 92.5%, 파싱 비중 54.0/60.0 = 90%로 병목이 파싱 축임을 짚고, 바인드 변수로 하드→소프트 전환해 라이브러리 캐시 경합을 줄이는 처방이 정확합니다 |
| ② | ✗ | Parse 40,000·Execute 40,000·Total 120,000은 모두 서버 내부의 콜 횟수이지 클라이언트 왕복 수가 아닙니다. 파싱 비용 축을 왕복 축으로 오인한 것으로, 커넥션 풀링·배열 인출은 24.0초의 파싱 CPU를 겨냥하지 못합니다 |
| ③ | ✗ | 재귀 Query 1,600,000(Execute 700,000 + Fetch 900,000)은 하드파싱이 부른 딕셔너리 조회의 논리 읽기라, 파싱을 없애면 함께 사라지는 종속 결과입니다. 버퍼 캐시(I/O 축)를 키워도 하드파싱 자체(파싱 축)는 그대로여서 원인을 다른 축에 오귀속한 것입니다 |
| ④ | ✗ | 재귀 미스 800회와 실작업 CPU 6.0초는 사실이지만, 파싱 비용 축과 계획 품질 축은 별개입니다. 통계가 최신이면 소프트파싱도 같은 계획을 재사용하므로, 하드파싱 37,000회를 유지해 얻는 계획 품질 이득은 없고 90%의 파싱 CPU만 낭비됩니다 |

## ✅ 이 문제의 핵심

1. **하드파싱율 = 라이브러리 캐시 미스 ÷ Parse 수.** 여기서는 37,000/40,000 = 92.5%로, 리터럴 SQL이라 거의 모든 파싱이 하드파싱입니다.
2. **하드파싱은 데이터 딕셔너리 재귀 조회를 유발**합니다. 재귀 블록의 Execute·Fetch·Query는 하드파싱의 종속 부하이지 독립된 병목이 아닙니다.
3. **파싱 비중 = (비재귀 Parse + 재귀 전체) CPU ÷ 전체 CPU = 54/60 = 90%.** 실작업은 6초(10%)뿐이라, 병목은 파싱 축입니다.
4. 파싱 축은 실행/계획/I/O·왕복 축과 독립입니다. 축을 뒤섞으면 버퍼 캐시·커넥션 풀링·계획 품질로 헛짚습니다.
5. 처방은 **바인드 변수**입니다. 하드→소프트 전환이 라이브러리 캐시 경합과 딕셔너리 재귀 조회를 동시에 없앱니다.

📌 한 줄 정리: 파싱 CPU가 전체의 90%(54/60초)이고 하드파싱율이 92.5%(37,000/40,000)이므로, 72초 병목은 버퍼 캐시·왕복·계획 품질이 아니라 파싱 축이며 바인드 변수로 하드파싱을 소프트파싱으로 돌려야 풀린다.
