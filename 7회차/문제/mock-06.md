## 문제 6

### 문제

피트니스 체인의 출입 정산 시스템에서 `출입기록` 테이블(약 4,800만 건)에는 결합 인덱스 `출입_IX = (클럽코드, 출입일시)`가 있다. 특정 클럽의 6월 입장 기록 중, 이용권 마스터(`이용권_PK = 이용권번호`)와 클럽 마스터(`클럽_PK = 클럽코드`)에 **모두 존재하는** 정합 건만 추리는 다음 SQL의 실행계획이다. 이 조회는 `출입기록`의 칼럼만 SELECT 하고, 두 마스터와의 조인은 존재 확인 용도이다.

```sql
SELECT e.출입번호, e.이용권번호, e.출입일시
  FROM 출입기록 e, 이용권 p, 클럽 s
 WHERE e.클럽코드 = 'C017'
   AND e.출입일시 >= DATE '2026-06-01'
   AND e.출입일시 <  DATE '2026-07-01'
   AND e.출입구분 = '입장'
   AND p.이용권번호 = e.이용권번호
   AND s.클럽코드  = e.클럽코드;
```

이 실행계획에 대한 설명으로 가장 적절한 것은?

#### [아 래]

```text
Id  Pid  Operation                                   ( Cost   Card   Bytes )
---------------------------------------------------------------------------
 0    -  SELECT STATEMENT                            (  742    790   37130 )
 1    0   NESTED LOOPS                               (  742    790   37130 )
 2    1    NESTED LOOPS                              (  740    810   34020 )
 3    2     TABLE ACCESS BY INDEX ROWID  출입기록      (  737    810   26730 )
 4    3      INDEX RANGE SCAN  출입_IX                (    8   3100         )
 5    2     INDEX UNIQUE SCAN  이용권_PK              (    0      1       9 )
 6    1     INDEX UNIQUE SCAN  클럽_PK                (    0      1       5 )
```

### 선택지

① 선두 칼럼 클럽코드의 등치와 두 번째 칼럼 출입일시의 범위가 `출입_IX`의 인덱스 액세스 조건이 되어 Id 4 INDEX RANGE SCAN이 Card 3,100을 내고, 인덱스에 없는 출입구분='입장'은 Id 3 TABLE ACCESS BY INDEX ROWID에서 필터로 걸러져 Card 810이 된다. 이용권_PK·클럽_PK는 존재만 확인해 테이블 액세스가 없다.

② 클럽코드 등치·출입일시 범위·출입구분 등치 세 조건이 함께 `출입_IX`의 인덱스 액세스 조건으로 처리되어 Id 4 INDEX RANGE SCAN의 스캔 시작·종료 지점을 좁힌다. Id 4의 Cost가 8로 낮은 것이 세 조건이 모두 인덱스에서 소진된 증거이며, Id 3 TABLE ACCESS BY INDEX ROWID는 SELECT 칼럼을 꺼내 오는 일만 한다.

③ `출입_IX`는 (클럽코드, 출입일시) 결합 인덱스이므로 선두 칼럼 클럽코드 조건이 빠지고 출입일시 범위만 주어져도 Id 4 INDEX RANGE SCAN이 Cost 8·Card 3,100 그대로 성립한다. 결합 인덱스는 구성 칼럼 중 하나라도 조건이 걸리면 스캔 시작점을 잡으므로, 선두 칼럼 유무는 이 플랜의 비용에 영향을 주지 않는다.

④ Id 5·Id 6의 INDEX UNIQUE SCAN이 내놓는 Bytes 9와 5는 이용권·클럽 테이블에서 읽어 온 행의 크기이므로, 두 유니크 스캔 뒤에는 TABLE ACCESS BY INDEX ROWID가 따라와 각 테이블 블록을 읽어야 Id 2·Id 1의 NESTED LOOPS 조인이 완성되고 최종 Card 790이 만들어진다. 두 마스터도 블록 I/O를 내는 셈이다.

### 정답 — ①

### 왜 ①인가

플랜의 세 노드에서 나온 **Card 값**을 위에서 아래로 훑으면 인덱스가 어디까지 걸러 주는지가 보입니다.

```text
INDEX RANGE SCAN 출입_IX            Card 3,100  ← 인덱스로 훑은 건수
TABLE ACCESS BY INDEX ROWID 출입기록 Card   810  ← 테이블 필터를 거친 뒤 남은 건수
NESTED LOOPS (최종)                 Card   790  ← 두 마스터 존재 확인까지 마친 건수
```

`출입_IX`는 `(클럽코드, 출입일시)` 순서입니다. WHERE에는 `클럽코드 = 'C017'`(등치)와 `출입일시` 범위가 있으므로, **선두 칼럼 등치 + 두 번째 칼럼 범위**까지가 인덱스로 연속해 훑을 수 있는 구간입니다. 그 결과가 INDEX RANGE SCAN의 3,100건입니다.

출입구분은 인덱스 칼럼이 아닙니다. 인덱스만으로는 걸러낼 수 없어, ROWID로 테이블 블록을 읽어 온 **Id 3 TABLE ACCESS BY INDEX ROWID 단계에서 필터**로 처리됩니다. 그래서 3,100건이 이 단계를 지나며 810건으로 줄어듭니다.

```text
3,100 (인덱스 액세스: 클럽코드=, 출입일시 범위)
  └─ 테이블 필터(출입구분='입장') 적용 → 810
        └─ 이용권_PK·클럽_PK 존재 확인(유니크 스캔) → 790 (최종)
```

Id 5·Id 6은 이용권번호·클럽코드가 마스터에 있는지만 확인하는 조인입니다. SELECT는 `출입기록` 칼럼만 뽑으므로 이용권·클럽 테이블에서 읽어 올 칼럼이 없어, **INDEX UNIQUE SCAN에서 끝나고 테이블 액세스로 내려가지 않습니다**(플랜에 두 테이블의 TABLE ACCESS 노드가 없다는 것이 그 표식입니다). ①이 이 구조를 정확히 서술합니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | 클럽코드(등치)·출입일시(범위)는 인덱스 액세스 조건, 출입구분은 인덱스에 없어 Id 3 테이블 필터 — Card가 3,100→810으로 줄고, 두 유니크 스캔은 테이블 액세스 없이 존재만 확인하는 흐름과 일치합니다 |
| ② | ✗ | Id 4의 Cost 8은 사실이나 출입구분은 `출입_IX` 구성 칼럼이 아니어서 인덱스 액세스 조건이 될 수 없습니다. 세 조건 전부가 스캔 범위를 좁혔다면 Id 4의 Card가 이미 810이었을 텐데 실제로는 3,100입니다 — 테이블 필터 몫을 인덱스 액세스로 끌어올린 서술입니다 |
| ③ | ✗ | 결합 인덱스는 선두 칼럼 클럽코드가 등치로 고정돼야 출입일시 범위가 연속 구간이 됩니다. 선두 조건이 빠지면 시작점을 잡지 못해 Cost 8·Card 3,100의 INDEX RANGE SCAN이 성립하지 않으므로, '구성 칼럼 중 하나만 있어도 된다'는 전제가 틀렸습니다 |
| ④ | ✗ | Id 5·Id 6의 Bytes 9·5는 조인 키를 인덱스에서 얻은 크기이지 테이블에서 읽은 행 크기가 아닙니다. 이용권·클럽 칼럼을 SELECT 하지 않아 두 노드는 INDEX UNIQUE SCAN에서 끝나며, 플랜에 두 테이블의 TABLE ACCESS 노드가 아예 없습니다 |

---

## ✅ 이 문제의 핵심

1. **결합 인덱스는 선두 칼럼 등치 + 다음 칼럼 범위까지가 액세스 조건.** 여기서는 클럽코드(=)·출입일시(범위)가 INDEX RANGE SCAN 구간을 만들어 3,100건을 냅니다.
2. **인덱스에 없는 칼럼은 테이블 필터.** 출입구분은 ROWID로 테이블을 읽은 뒤 Id 3 TABLE ACCESS BY INDEX ROWID 단계에서 걸러져 810건으로 줄어듭니다.
3. **선두 칼럼이 빠지면 RANGE SCAN 효율이 무너집니다.** 선두 등치가 스캔 시작점을 고정해 줘야 두 번째 칼럼 범위가 연속 구간이 됩니다.
4. **필요한 칼럼이 없으면 인덱스 유니크 스캔에서 끝납니다.** Id 5·Id 6은 존재 확인만 하므로 테이블 액세스로 내려가지 않습니다 — 플랜에 해당 TABLE ACCESS 노드가 없다는 것이 근거입니다.

📌 한 줄 정리: 클럽코드 등치와 출입일시 범위는 `출입_IX` 인덱스 액세스 조건이 되어 3,100건을 내고, 인덱스에 없는 출입구분은 Id 3 테이블 필터로 810건까지 줄이며, 칼럼을 뽑지 않는 두 마스터 조인은 INDEX UNIQUE SCAN에서 끝나 테이블 액세스가 없다.
