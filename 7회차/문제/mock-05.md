## 문제 5

### 문제

음원 스트리밍 서비스에서 `재생이력`(약 1억 2,000만 건)을 `청취자`(약 800만 건), `곡마스터`(약 5만 건)와 조인해 아이템별 재생 집계 3,000행을 뽑는 정산 SQL의 TKPROF이다. 재생이력 Full Scan은 몇 초 만에 끝날 것으로 봤는데 응답이 50초를 넘겨 느리다는 신고가 들어왔다. 아래 트레이스에 대한 해석으로 가장 적절한 것은?

(단, 옵티마이저 통계는 최신이고 CPU·디스크 자원의 외부 경합은 없으며, 세 테이블 모두 인덱스가 없어 Full Scan + Hash Join으로만 수행된다.)

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.008         0.008        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch          4     9.000        50.000   260000   2000000         0      3000
--------------------------------------------------------------------------------
Total          6     9.008        50.008   260000   2000000         0      3000

Rows        Row Source Operation
--------------------------------------------------------------------------------
     3000   HASH GROUP BY (cr=2000000 pr=260000 pw=176000 time=48000000 us)
120000000     HASH JOIN (cr=2000000 pr=260000 pw=176000 time=47000000 us)
    50000       TABLE ACCESS FULL 곡마스터 (cr=2000 pr=0 pw=0 time=60000 us)
120000000       HASH JOIN (cr=1998000 pr=260000 pw=176000 time=44000000 us)
  8000000         TABLE ACCESS FULL 청취자 (cr=98000 pr=8000 pw=0 time=1500000 us)
120000000         TABLE ACCESS FULL 재생이력 (cr=1900000 pr=76000 pw=0 time=9000000 us)
```

### 선택지

① Fetch 4회에 몰린 CPU Time 9.000초가 Elapsed 50.000초의 골격이고, 1억 2,000만 행을 흘려보내는 안쪽 HASH JOIN(time=44초)이 그 CPU를 쓴 지점이다. 세 테이블 모두 인덱스가 없어 Full Scan + Hash Join으로만 도는 CPU 바운드이므로, 병렬도(DOP)를 높여 CPU를 여러 서버에 나눠 주면 50초가 개선된다.

② 논리 I/O 200만 중 26만이 디스크라 BCHR은 87.0%인데, 물리 읽기 260,000의 대부분은 안쪽 HASH JOIN이 `청취자` 800만 행을 build하다 워크에어리어를 넘겨 temp로 흘린 spill이다(pw=176,000). 병목은 재생이력 스캔이 아니라 해시 조인의 디스크 spill이므로, PGA(해시 영역)를 키워 spill을 없애야 한다.

③ cr 200만 중 `재생이력` Full Scan이 1,900,000으로 논리 읽기의 95%를 차지하고, 그 노드가 1억 2,000만 행을 흘려보내며 물리 읽기도 pr=76,000을 냈다. 병목은 1억 2,000만 건 재생이력 스캔이므로, 재생일시에 인덱스를 만들어 이 Full Scan을 줄이면 물리 읽기 260,000도 함께 줄어 50초가 해소된다.

④ BCHR 87.0%는 논리 읽기 2,000,000 대비 물리 읽기 260,000이 13%나 된다는 뜻이라 디스크가 병목이고, Elapsed 50.000초에서 CPU 9.000초를 뺀 41.0초가 곧 그 물리 읽기 대기다. 인덱스 없이 Full Scan만 도는 이 SQL은 캐시 적중률이 곧 응답이므로, DB 버퍼 캐시를 키워 260,000 블록을 적중으로 돌리면 41초가 사라진다.

---

### 정답 — ②

### 왜 ②인가

먼저 **BCHR**로 논리 대비 물리 읽기를 봅니다.

```text
BCHR = ((Query + Current) − Disk) / (Query + Current) × 100
     = (2,000,000 + 0 − 260,000) / 2,000,000 × 100
     = 1,740,000 / 2,000,000 × 100 = 87.0%
디스크 물리 읽기 비중 = 260,000 / 2,000,000 × 100 = 13.0%
```

다음은 **시간의 정체**입니다.

```text
CPU 비중 = 9.000 / 50.000 × 100 = 18.0%   → 나머지 82%가 대기
Elapsed − CPU = 50.000 − 9.000 = 41.0초    ← 기다린 시간
```

응답의 82%가 대기입니다. 대기가 난 곳을 Row Source로 찾되, **cr(논리)과 pr·pw(물리·temp)를 분리**해서 봐야 합니다.

```text
테이블 스캔 물리 읽기 = 재생이력 76,000 + 청취자 8,000 = 84,000
안쪽 HASH JOIN pr = 260,000, pw = 176,000
  → 스캔이 읽은 84,000을 빼면 260,000 − 84,000 = 176,000이 spill 재읽기
물리 읽기 260,000 중 spill 비중 = 176,000 / 260,000 × 100 ≈ 67.7%
```

`pw=176,000`은 결정적입니다. 안쪽 HASH JOIN이 `청취자` 800만 행을 build하다 해시 영역을 넘겨 **temp로 spill**했고, 그 176,000 블록을 다시 읽느라 물리 읽기의 약 68%가 발생했습니다. 시간도 이 노드에 몰립니다.

```text
재생이력 Full Scan time = 9.0초   ← 큰 테이블이지만 멀티블록이라 빠름
안쪽 HASH JOIN time         = 44.0초  ← spill I/O로 정체된 지점
```

cr은 재생이력 Full Scan(1,900,000, 95%)이 지배하지만, 그 스캔은 9초 만에 끝났습니다. 50초를 만든 것은 논리 읽기가 아니라 **해시 조인의 디스크 spill(pw=176,000)**입니다. 따라서 처방은 PGA(해시 영역) 확대이며, ②가 BCHR과 병목 지목을 모두 옳게 했습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | 안쪽 HASH JOIN의 time=44초는 맞지만 그 44초는 CPU가 아니라 spill I/O 대기입니다. CPU 9.000초는 Elapsed 50.000초의 18%뿐이라 CPU 바운드가 아니므로, DOP 상향은 원인을 잘못 짚은 것입니다 |
| ② | **○** | BCHR (2,000,000−260,000)/2,000,000 = 87.0%가 정확하고, pw=176,000과 물리 읽기의 68%가 안쪽 HASH JOIN의 spill임을 짚어 PGA를 처방한 것이 맞습니다 |
| ③ | ✗ | cr 1,900,000(95%)과 pr=76,000은 사실이나 그 스캔은 time 9초로 빠릅니다. 50초 정체는 논리 읽기가 아니라 pw=176,000의 spill이라, 인덱스로 cr을 줄여도 spill 재읽기 176,000은 남으므로 병목을 오귀속한 처방입니다 |
| ④ | ✗ | 41.0초가 대기라는 뺄셈은 맞지만, 물리 읽기 260,000의 68%(176,000)는 temp spill 재읽기라 DB 버퍼 캐시로는 캐시되지 않습니다. BCHR 87.0%를 근거로 캐시를 키워도 spill 대기 41초는 남아, 대기의 원인을 캐시로 오귀속한 것입니다 |

---

## ✅ 이 문제의 핵심

1. **BCHR = ((Query+Current)−Disk)/(Query+Current)×100.** 여기서는 (2,000,000−260,000)/2,000,000 = 87.0%입니다.
2. **cr(논리)과 pr·pw(물리·temp)를 분리**해야 합니다. cr은 재생이력 Full Scan(95%)이 지배해도, 시간을 만든 건 pw=176,000의 해시 조인 spill입니다.
3. **`pw>0`은 해시 영역 spill의 신호**입니다. 물리 읽기 260,000 중 176,000(68%)이 spill 재읽기이고, 테이블 스캔 물리는 84,000뿐입니다.
4. build input이 큰 노드(청취자 800만 행)가 워크에어리어를 넘기면 spill합니다 — 병목은 build 쪽 조인이지 probe 쪽 큰 테이블 스캔이 아닙니다.
5. 처방은 **PGA(해시 영역) 확대**입니다. DOP·인덱스·버퍼 캐시는 41초의 spill 대기를 겨냥하지 못합니다.

📌 한 줄 정리: BCHR 87%까지 옳게 읽어도, 물리 읽기 260,000의 68%가 pw=176,000의 해시 조인 spill이라는 사실을 놓치면 병목을 CPU·재생이력 스캔·버퍼 캐시로 오귀속하게 된다.
