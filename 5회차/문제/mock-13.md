## 문제 13

### 문제

구매발주 조회 화면은 발주상태코드 값만 바꿔 가며 리터럴을 SQL 텍스트에 직접 박아 넣는 방식으로 질의를 던진다. 세션에 `CURSOR_SHARING = FORCE`를 걸고 상태코드 'S1'·'S2'·'S3'로 세 번 조회한 뒤 라이브러리 캐시(v$sql)를 요약한 결과가 아래와 같다. `CURSOR_SHARING`과 커서 공유에 대한 설명으로 가장 적절하지 <u>않은</u> 것은?

#### [아 래]

```sql
-- 세션 기본: ALTER SESSION SET CURSOR_SHARING = FORCE;
select 품목명 from 발주 where 발주상태코드 = 'S1';
select 품목명 from 발주 where 발주상태코드 = 'S2';
select 품목명 from 발주 where 발주상태코드 = 'S3';
```

```text
[ 라이브러리 캐시(v$sql) 요약 — CURSOR_SHARING=FORCE ]
SQL_ID           SQL_TEXT (선두 요약)                                    PARSE_CALLS  EXECUTIONS  LOADS
---------------------------------------------------------------------------------------------------------
h7k3m9r2t5wqz    select 품목명 from 발주 where 발주상태코드 = :"SYS_B_0"        3           3         1
```

### 선택지

① `CURSOR_SHARING=FORCE`는 SQL 텍스트의 리터럴('S1'·'S2'·'S3')을 시스템 생성 바인드 변수(`:"SYS_B_0"`)로 치환하므로, 값만 다른 세 SQL이 하나의 부모 커서(h7k3…)를 공유한다.

② `CURSOR_SHARING=FORCE`는 리터럴뿐 아니라 키워드 대소문자·공백·힌트까지 정규화하므로, 대소문자나 공백만 달라진 SQL도 자동으로 같은 커서로 합쳐진다.

③ 리터럴을 바인드로 치환해 공유하면 하드파싱(LOADS)은 한 번으로 줄지만, 값 분포가 편중된 칼럼에서는 첫 실행의 바인드 값에 맞춰진 계획을 이후 값들이 그대로 쓰는 바인드 변수 엿보기(bind peeking)의 부작용이 생길 수 있다.

④ 기본값 EXACT였다면 'S1'·'S2'·'S3' 세 리터럴이 각각 다른 SQL_ID로 하드파싱되지만, FORCE에서는 v$sql에 `:"SYS_B_0"`를 담은 커서 하나만 남고 EXECUTIONS가 3으로 누적된다.

---

### 정답 — ②

### 왜 ②인가

v$sql 요약이 곧 근거입니다. 리터럴만 다른 세 SQL이 `CURSOR_SHARING=FORCE` 아래에서 **SQL_ID 하나(h7k3…)** 로 합쳐졌고, SQL_TEXT의 리터럴 자리가 `:"SYS_B_0"`로 바뀌었습니다. `PARSE_CALLS 3 / EXECUTIONS 3 / LOADS 1`은 세 번 파싱을 요청했지만 커서는 **한 번만 적재(하드파싱 1회)** 하고 이후엔 공유(소프트파싱)했다는 뜻입니다.

```text
'S1' ┐
'S2' ┼→ FORCE가 리터럴을 :"SYS_B_0" 로 치환 → 텍스트 동일 → SQL_ID 하나
'S3' ┘   LOADS 1 (하드파싱 1회), EXECUTIONS 3 (세 번 실행 누적)
```

`CURSOR_SHARING=FORCE`가 하는 일은 **리터럴 상수를 바인드 변수로 치환**하는 것뿐입니다. 키워드 대소문자·공백·힌트는 건드리지 않으므로, 리터럴 외의 요소가 다르면 텍스트는 여전히 다른 것으로 간주되어 별도 커서로 갈립니다. ②는 "FORCE가 대소문자·공백·힌트까지 정규화해 합쳐 준다"는 **정규화 가정의 오류**입니다. 만약 ②처럼 정규화까지 한다면 그것은 FORCE의 동작 범위를 넘는 진술입니다. 그래서 부적절한 것은 ②입니다.

①④는 요약표가 보여 주는 리터럴 치환·커서 공유·EXECUTIONS 누적을 정확히 서술하고, ③은 공유의 대가로 따라오는 바인드 변수 엿보기 부작용을 옳게 짚습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ○ | FORCE가 리터럴을 `:"SYS_B_0"`로 치환해 값만 다른 세 SQL이 h7k3… 커서 하나로 공유됩니다. 요약표의 SQL_ID 단일화가 그 증거입니다 |
| ② | **✗** | FORCE는 리터럴만 바인드로 치환할 뿐 대소문자·공백·힌트는 정규화하지 않습니다. 그 요소가 다르면 텍스트가 달라 여전히 별도 커서입니다 |
| ③ | ○ | 리터럴을 바인드화하면 하드파싱은 줄지만, 편중된 칼럼에서는 첫 바인드 값에 맞춘 계획을 이후 값이 재사용하는 엿보기 부작용이 생길 수 있습니다 |
| ④ | ○ | EXACT였다면 세 리터럴이 각각 다른 SQL_ID로 하드파싱되지만, FORCE에선 `:"SYS_B_0"` 커서 하나만 남고 EXECUTIONS가 3으로 누적됩니다 — 요약표 그대로입니다 |

---

## ✅ 이 문제의 핵심

1. **`CURSOR_SHARING=FORCE`는 리터럴 상수를 시스템 생성 바인드 변수로 치환**합니다. 값만 다른 SQL을 하나의 커서로 공유시킵니다.
2. **FORCE는 대소문자·공백·힌트를 정규화하지 않습니다.** 리터럴 외의 요소가 다르면 텍스트가 달라 여전히 별도 SQL_ID입니다.
3. **LOADS는 하드파싱 횟수, EXECUTIONS는 실행 횟수**입니다. LOADS 1·EXECUTIONS 3은 한 번 적재해 세 번 공유했다는 뜻입니다.
4. **공유에는 대가가 따릅니다** — 값이 편중된 칼럼에서 바인드로 묶으면 첫 실행의 계획이 굳어지는 바인드 변수 엿보기 부작용을 감수해야 합니다.

📌 한 줄 정리: `CURSOR_SHARING=FORCE`는 리터럴만 바인드 변수로 치환해 값만 다른 SQL을 한 커서로 공유시킬 뿐, 대소문자·공백·힌트까지 정규화하지는 않습니다 — "그런 요소까지 정규화해 합쳐 준다"는 ②가 부적절합니다.
