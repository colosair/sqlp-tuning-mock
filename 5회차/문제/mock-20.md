## 문제 20

### 문제

입찰 마감 작업에서 세션 41이 입찰 테이블 전체에 `LOCK TABLE 입찰 IN SHARE MODE`를 건 상태다. 그 사이 세션 55가 특정 입찰 건의 낙찰가를 `UPDATE`하려 한다. 이때 `v$lock`을 조회한 결과가 아래와 같다. 이 테이블 수준 락(TM) 상태에 대한 해석으로 가장 적절하지 <u>않은</u> 것은?

#### [아 래]

```text
[ v$lock — 입찰 테이블에 걸린 TM(테이블) 락 ]
SID   TYPE   ID1       ID2   LMODE   REQUEST   BLOCK
-----------------------------------------------------
 41   TM     54021      0      4        0        1
 55   TM     54021      0      0        3        0

* TM 모드 코드:  2=RS(Row Share)  3=RX(Row Exclusive)  4=S(Share)  5=SRX  6=X(Exclusive)
* SID 41 : LOCK TABLE 입찰 IN SHARE MODE 로 테이블에 S(4) 보유(BLOCK=1)
* SID 55 : UPDATE … 가 테이블에 RX(3)를 REQUEST 하며 대기
```

### 선택지

① 세션 41은 `LOCK TABLE … IN SHARE MODE`로 테이블 전체에 S(4) 모드 TM 락을 보유(BLOCK=1)한다. 이는 개별 행을 잠그는 TX 락이 아니라 오브젝트(테이블) 수준 락이다.

② 세션 55의 UPDATE는 DML이므로 갱신에 앞서 테이블에 RX(3) 모드 TM 락을 요청하는데, 이미 걸린 S(4)와 호환되지 않아 락을 얻지 못하고 REQUEST=3 상태로 대기한다.

③ S(4)와 RX(3)는 서로 호환되는 모드이므로, 세션 55의 UPDATE는 대기 없이 TM 락을 획득해 곧바로 갱신을 진행한다.

④ 세션 62가 같은 테이블에 다시 `LOCK TABLE … IN SHARE MODE`를 실행하면 S(4)끼리는 호환되어 41과 나란히 락을 얻고 대기하지 않지만, 그 상태에서도 세션 55의 RX(3) 요청은 여전히 막힌다.

---

### 정답 — ③

### 왜 ③인가

TM(테이블) 락은 오브젝트 단위 락이고, 모드 사이의 **호환성**이 대기 여부를 결정합니다. 표를 읽으면 S(4) 보유와 RX(3) 요청이 충돌하는 그림이 드러납니다.

```text
SID 41 : TM 54021  LMODE=4(S)   BLOCK=1        → LOCK TABLE IN SHARE MODE 로 테이블 S 보유
SID 55 : TM 54021  REQUEST=3(RX)               → UPDATE가 RX 요청 → S와 비호환 → 대기

  [TM 호환성]  S(4) vs RX(3) = 비호환
               S(4) vs S(4)  = 호환    (여러 세션이 함께 SHARE 가능)
```

③은 호환성을 정반대로 뒤집었습니다. 오라클 TM 락에서 **S(4)와 RX(3)는 비호환**입니다 — SHARE 모드로 테이블을 잠근 동안에는 다른 세션의 DML(RX 요청)이 막힙니다. 표의 세션 55가 `REQUEST=3`으로 대기 중인 것이 바로 그 증거입니다. 그런데 ③은 "S와 RX가 호환이라 UPDATE가 대기 없이 진행된다"고 했으니, 표가 보여 주는 대기 상태와 정면으로 어긋납니다. 그래서 부적절한 것은 ③입니다.

①은 41이 보유한 것이 행 단위 TX가 아닌 테이블 수준 TM(S 모드)임을, ②는 55의 UPDATE가 RX를 요청하다 비호환으로 대기함을, ④는 S끼리는 호환이지만 RX 요청은 여전히 막힘을 옳게 설명합니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ○ | 41의 락은 `ID1=54021` 오브젝트에 걸린 S(4) 모드 TM 락으로, 행 단위 TX 락이 아니라 테이블 수준 락입니다. BLOCK=1로 상대를 막고 있습니다 |
| ② | ○ | UPDATE는 갱신 전 테이블에 RX(3)를 요청하는데 S(4)와 비호환이라 얻지 못하고 REQUEST=3으로 대기합니다. 표의 두 번째 행 그대로입니다 |
| ③ | **✗** | S(4)와 RX(3)는 비호환입니다. SHARE 락이 걸린 동안 DML의 RX 요청은 막혀 대기하는데, ③은 호환이라 즉시 진행한다고 반대로 서술했습니다 |
| ④ | ○ | S(4)끼리는 호환이라 62가 41과 함께 SHARE를 보유해 대기하지 않지만, RX(3)는 S와 비호환이라 55의 요청은 그대로 막힙니다 |

---

## ✅ 이 문제의 핵심

1. **TM 락은 테이블(오브젝트) 수준 락**입니다. 행을 식별하는 TX 락과 층위가 다르며, `LOCK TABLE`·DDL·DML이 각기 다른 TM 모드를 겁니다.
2. **`LOCK TABLE … IN SHARE MODE`는 S(4) 모드 TM 락**을 겁니다. 조회는 허용하되 다른 세션의 DML(RX 요청)은 막습니다.
3. **S(4)와 RX(3)는 비호환**입니다. SHARE가 걸린 동안 UPDATE·INSERT·DELETE는 RX를 얻지 못해 대기합니다.
4. **S(4)끼리는 호환**이라 여러 세션이 함께 SHARE로 잠글 수 있지만, 그 사이에도 RX 요청은 계속 막힙니다.

📌 한 줄 정리: `LOCK TABLE … IN SHARE MODE`가 건 S(4) TM 락은 DML의 RX(3) 요청과 비호환이라 세션 55가 대기하는데, "S와 RX가 호환이라 즉시 갱신한다"는 ③은 호환성을 정반대로 뒤집어 부적절합니다.
