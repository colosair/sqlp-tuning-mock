## 문제 16

### 문제

민원 접수 테이블은 접수지역코드(2자리 VARCHAR2)를 기준으로 아래처럼 LIST 파티셔닝되어 있다. 파티셔닝의 목적과 Partition Pruning의 작동에 대한 설명으로 가장 적절하지 <u>않은</u> 것은?

#### [아 래]

```sql
CREATE TABLE 민원 (
    민원번호      NUMBER,
    접수지역코드   VARCHAR2(2),
    접수일자      DATE,
    처리상태      VARCHAR2(10)
)
PARTITION BY LIST (접수지역코드) (
    PARTITION p_seoul    VALUES ('11'),
    PARTITION p_busan    VALUES ('26'),
    PARTITION p_incheon  VALUES ('28'),
    PARTITION p_gyeonggi VALUES ('41'),
    PARTITION p_etc      VALUES (DEFAULT)
);
```

### 선택지

① `WHERE SUBSTR(접수지역코드, 1, 2) = '11'` 조건은 접수지역코드의 앞 두 자리를 그대로 뽑은 것이라 값이 코드 자체와 같으므로, 옵티마이저가 p_seoul 한 파티션으로 Pruning한다.

② `WHERE 접수지역코드 = '26'` 조건은 파티션 키를 가공하지 않았으므로, 옵티마이저가 값을 파티션 목록과 대조해 p_busan 한 파티션만 접근한다.

③ 파티셔닝의 목적은 성능(Pruning으로 스캔량 축소)에 국한되지 않는다. 파티션 단위 백업·`DROP PARTITION` 같은 관리성과, 한 파티션의 장애·작업이 다른 파티션 가용성에 미치는 영향을 줄이는 가용성도 포함된다.

④ `WHERE 접수지역코드 IN ('11','41')` 조건은 두 리터럴이 각각 파티션 목록과 대조돼 p_seoul·p_gyeonggi 두 파티션만 읽고 나머지는 건너뛰므로 Pruning이 작동한다.

---

### 정답 — ①

### 왜 ①인가

Partition Pruning은 옵티마이저가 **WHERE 조건의 값을 파티션 정의(LIST 값 목록)와 대조**해 접근할 파티션을 미리 좁히는 최적화입니다. 이 대조가 가능하려면 조건이 **파티션 키 칼럼(접수지역코드) 자체**에 걸려 있어야 합니다.

```text
② 접수지역코드 = '26'          → 목록 대조 → p_busan 1개
④ 접수지역코드 IN ('11','41')  → 목록 대조 → p_seoul, p_gyeonggi 2개 (나머지 스킵)
① SUBSTR(접수지역코드,1,2)='11' → 키에 함수 → 목록과 대조 불가 → 전 파티션 스캔
```

①은 `SUBSTR(접수지역코드, 1, 2)`로 **파티션 키에 함수를 씌웠습니다.** 접수지역코드가 이미 2자리라 결과값이 원래 코드와 논리적으로 같더라도, 옵티마이저는 함수의 결과를 LIST 값 목록과 미리 대조할 수 없어 Pruning을 포기하고 `p_seoul … p_etc` **모든 파티션을 스캔**한 뒤 각 행에서 SUBSTR를 평가해 필터합니다. "앞 두 자리를 뽑았을 뿐이라 값이 같다"는 부분적 진실이 함정으로, 함수 한 줄이 최선(1개 파티션)을 최악(전 파티션 스캔)으로 뒤집습니다. 그래서 Pruning이 작동한다고 볼 수 없는 것은 ①입니다.

②④는 키를 가공하지 않은 조건이라 목록과 대조돼 필요한 파티션만 접근하고, ③은 파티셔닝 목적이 성능뿐 아니라 관리성·가용성까지 아우른다는 점을 옳게 설명합니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **✗** | 파티션 키에 `SUBSTR`를 씌워 값 목록과 대조가 불가능해집니다. 값이 코드와 같아도 전 파티션을 스캔한 뒤 필터하므로 Pruning이 깨집니다 |
| ② | ○ | 키를 가공하지 않은 등치 조건이라 '26'을 목록과 대조해 p_busan 한 파티션만 접근합니다. Pruning 작동합니다 |
| ③ | ○ | 파티셔닝 목적은 성능만이 아니라 파티션 단위 관리성과 장애 격리 가용성을 포함합니다. 표준적 서술입니다 |
| ④ | ○ | 두 리터럴을 각각 목록과 대조해 p_seoul·p_gyeonggi 두 파티션만 읽고 나머지는 건너뛰므로 Pruning이 작동합니다 |

---

## ✅ 이 문제의 핵심

1. **Partition Pruning은 파티션 키에 직접 걸린 조건에서만 작동**합니다. 키를 함수로 가공하면 파티션 정의와 대조할 수 없습니다.
2. **LIST 파티셔닝은 값 목록과 등치·IN 조건을 대조**해 해당 파티션만 남깁니다. 여러 값이면 여러 파티션이 남되 나머지는 건너뜁니다.
3. **`SUBSTR`·`TO_CHAR` 등 키 가공은 결과가 원값과 같아 보여도 Pruning을 무력화**합니다. "앞자리만 뽑았다"는 부분적 타당함이 함정입니다.
4. **파티셔닝의 목적은 성능·관리성·가용성**입니다 — Pruning 성능만이 아니라 파티션 단위 관리와 장애 격리도 노립니다.

📌 한 줄 정리: 키를 가공하지 않은 조건은 값 목록과 대조돼 Pruning되지만, `SUBSTR(접수지역코드,…)`처럼 키에 함수를 씌우면 결과가 같아 보여도 대조가 불가능해져 전 파티션을 스캔합니다.
