## 문제 8

### 문제

리프 레벨에 행 데이터를 정렬해 담는 클러스터형 인덱스(SQL Server)·IOT(오라클)와 리프에 키+행 위치만 담는 일반 B-Tree 인덱스, 그리고 Index Unique Scan에 대한 설명으로 가장 적절한 것은?

### 선택지

① SQL Server의 비클러스터형(nonclustered) 인덱스는 리프 블록에 행 데이터 전체를 인덱스 키 순서로 담고 있어, 그 인덱스만 읽으면 어떤 컬럼을 조회하든 원본 테이블을 되짚지 않고 결과를 낼 수 있다.

② 클러스터형 인덱스는 리프가 곧 데이터이므로 한 테이블에 여러 개를 만들어 두면 조회마다 서로 다른 정렬본을 골라 써서, 어떤 검색 조건이 들어와도 테이블 액세스 없이 커버링으로 처리된다.

③ 오라클의 IOT나 SQL Server의 클러스터형 인덱스는 리프 레벨에 행 데이터를 인덱스 키 순서로 저장하므로, 키로 조회하면 리프에 도달하는 것만으로 행을 얻어 힙 테이블을 되짚는 ROWID/RID 액세스가 필요 없다.

④ 유일(UNIQUE) 인덱스에 등가 조건을 주어 일어나는 Index Unique Scan은, 조건을 만족하는 행이 여러 건이더라도 리프 블록을 오른쪽으로 계속 이어 읽어 해당 행을 모두 훑은 뒤 종료한다.

---

### 정답 — ③

### 왜 ③인가

두 인덱스는 **리프 레벨에 무엇이 있는가**로 갈립니다. 이 차이가 테이블을 되짚는 추가 액세스의 유무를 결정합니다.

```text
일반 B-Tree 인덱스 (오라클 힙 테이블 인덱스 · SQL Server 비클러스터형)
   리프 : 인덱스 키 + 행 위치(ROWID/RID)
   조회 : 인덱스에 없는 컬럼이 필요하면 ROWID/RID로 테이블을 되짚는
          추가 Random 액세스(테이블 액세스 / key lookup)가 발생

클러스터형 인덱스(SQL Server) · IOT(오라클)
   리프 : 인덱스 키 순서로 정렬된 '행 데이터 그 자체'
   조회 : 키로 리프에 도달하면 거기 행이 있으므로 되짚기 불필요
   제약 : 물리적 정렬은 하나뿐 → 테이블당 하나만 가능
```

③은 이 성질을 정확히 짚었습니다. IOT·클러스터형 인덱스는 리프가 곧 데이터라, 키로 찾아 리프에 닿으면 그 자리에서 행을 얻어 별도의 ROWID/RID 되짚기가 필요 없습니다.

①·②·④는 각 개념의 **경계를 뭉갠** 함정입니다.

- ①은 클러스터형의 성질(리프=데이터)을 **비클러스터형**에 갖다 붙였습니다. 비클러스터형 리프에는 키와 RID만 있어, 인덱스에 없는 컬럼이 필요하면 테이블을 되짚어야 합니다.
- ②는 "리프가 곧 데이터"라는 성질에서 물리 정렬이 하나뿐이라는 제약을 빠뜨렸습니다. 클러스터형 인덱스는 **테이블당 하나**이므로 "여러 개를 만들어 조회마다 다른 정렬본을 고른다"는 성립하지 않습니다.
- ④는 Index Unique Scan과 Range Scan의 경계를 지웠습니다. Unique Scan은 유일성이 보장돼 **최대 한 건**을 찾으면 즉시 멈춥니다. 여러 건을 이어 훑는 것은 Range Scan입니다.

---

## ✅ 이 문제의 핵심

1. 인덱스는 **리프에 무엇이 있는가**로 갈립니다. 일반 B-Tree·비클러스터형은 **키+ROWID/RID**, 클러스터형·IOT는 **행 데이터 그 자체**입니다.
2. **클러스터형·IOT는 키로 리프에 닿으면 되짚기가 불필요**합니다. 비클러스터형은 인덱스에 없는 컬럼이 필요하면 테이블을 되짚습니다.
3. 클러스터형 인덱스는 **물리 정렬이 하나뿐이라 테이블당 하나**만 만들 수 있습니다.
4. **Index Unique Scan = 최대 한 건 찾고 즉시 종료.** 여러 건을 이어 훑는 것은 Range Scan입니다.

📌 한 줄 정리: IOT·클러스터형 인덱스는 리프가 곧 데이터라 키 조회 시 힙 테이블 되짚기가 필요 없으며, 비클러스터형은 키+RID만 담고 클러스터형은 테이블당 하나, Unique Scan은 한 건에서 멈춘다는 경계를 지켜야 합니다.
