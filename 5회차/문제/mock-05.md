## 문제 5

### 문제

항만 물류 시스템에서 컨테이너반출입 테이블(약 9,000만 건)과 선박 테이블(약 4만 건)을 조인해 선박별 반출입 건수를 집계하는 SQL의 TKPROF 결과이다. 아래 트레이스에 대한 해석으로 가장 적절한 것은?

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.006         0.006        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch        501     8.994        71.994   200000   2500000         0      5000
--------------------------------------------------------------------------------
Total        503     9.000        72.000   200000   2500000         0      5000

Rows       Row Source Operation
--------------------------------------------------------------------------------
   5000     HASH GROUP BY (cr=2500000 pr=200000 pw=0 time=71900000 us)
90000000      HASH JOIN  (cr=2500000 pr=200000 pw=0 time=70500000 us)
  40000         TABLE ACCESS FULL 선박 (cr=140000 pr=9000 pw=0 time=1800000 us)
90000000        TABLE ACCESS FULL 컨테이너반출입 (cr=2360000 pr=191000 pw=0 time=66500000 us)
```

### 선택지

① CPU Time 9초가 Elapsed 72초를 좌우하는 CPU 바운드이므로, 병렬도(DOP)를 높여 CPU를 분산하는 것이 최우선 처방이다.

② Row Source에 인덱스 스캔이 없으니 선박 테이블(4만 건)의 인덱스 부재가 병목이며, 선박에 인덱스를 만들면 72초가 해소된다.

③ 논리 I/O 250만 블록 중 20만(약 8%)을 디스크에서 읽어 BCHR은 약 92%이며, CPU 9초는 Elapsed 72초의 약 12.5%뿐이라 나머지 약 63초가 대기다. cr·pr·time이 모두 컨테이너반출입 Full Scan(cr=2,360,000, pr=191,000, time≈66.5초)에 집중되므로 병목은 9,000만 건 컨테이너반출입 테이블 액세스다.

④ pr 200,000과 BCHR 92%로 보아 HASH JOIN의 해시 영역이 디스크로 스필한 것이 원인이므로, PGA를 키워 스필을 없애면 약 63초의 대기가 사라진다.

---

### 정답 — ③

### 왜 ③인가

먼저 **BCHR**로 논리 대비 물리 읽기의 비율을 확인합니다.

```text
BCHR = ((Query + Current) − Disk) / (Query + Current) × 100
     = (2,500,000 + 0 − 200,000) / 2,500,000 × 100
     = 2,300,000 / 2,500,000 × 100 = 92.0%
디스크 물리 읽기 비중 = 200,000 / 2,500,000 × 100 = 8.0%
```

논리 250만 블록 중 8%를 디스크에서 물리적으로 읽었습니다. 다음은 **시간의 정체**입니다.

```text
CPU 비중 = 9.000 / 72.000 × 100 = 12.5%    → 나머지 약 87.5%가 대기
Elapsed − CPU = 72.000 − 9.000 = 63.0초     ← 일한 시간이 아니라 기다린 시간
```

응답시간의 대부분이 대기이고, 그 대기가 어디서 났는지는 Row Source가 지목합니다.

```text
컨테이너반출입 cr 비중 = 2,360,000 / 2,500,000 × 100 = 94.4%   ← 블록 소비의 대부분
컨테이너반출입 pr 비중 =   191,000 /   200,000 × 100 ≈ 95.5%   ← 물리 읽기의 대부분
컨테이너반출입 time    = 66.5초 (전체 Elapsed 72초의 대부분)
선박 cr 비중          =   140,000 / 2,500,000 × 100 ≈ 5.6%    ← 소량
```

블록 소비(cr)·물리 읽기(pr)·소요 시간(time)이 **세 지표 모두 컨테이너반출입 Full Scan 한 노드**에 몰려 있고, HASH JOIN의 `pw=0`이라 해시 영역 디스크 스필도 없습니다. 따라서 병목은 9,000만 건 컨테이너반출입 테이블의 Full Scan I/O이며, ③이 BCHR 해석과 병목 지목을 모두 옳게 했습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | CPU 9초는 Elapsed 72초의 12.5%뿐이라 CPU 바운드가 아닙니다. 응답시간의 약 87.5%(약 63초)가 컨테이너반출입 Full Scan의 I/O 대기이므로 DOP만 올리는 것은 원인 오귀속입니다 |
| ② | ✗ | 인덱스 스캔이 없는 것은 사실이나, 병목은 cr 5.6%뿐인 선박이 아니라 cr 94.4%의 컨테이너반출입 Full Scan입니다. 선박 인덱스는 63초 대기를 겨냥하지 못합니다 |
| ③ | **○** | (2,500,000−200,000)/2,500,000 = 92.0%로 BCHR이 정확하고, cr(94.4%)·pr(95.5%)·time(66.5초)이 모두 컨테이너반출입 Full Scan에 집중되어 병목 지목이 맞습니다 |
| ④ | ✗ | HASH JOIN의 `pw=0`이라 해시 영역 디스크 스필은 없습니다. pr 200,000은 스필이 아니라 컨테이너반출입 Full Scan의 물리 읽기이므로, PGA 확대는 63초 대기를 겨냥하지 못한 헛짚은 처방입니다 |

---

## ✅ 이 문제의 핵심

1. **BCHR = ((Query+Current)−Disk)/(Query+Current)×100.** 여기서는 (2,500,000−200,000)/2,500,000 = 92.0%입니다.
2. **CPU 비중(12.5%)이 낮으면 CPU 바운드가 아닙니다.** Elapsed−CPU(63초)가 대기이고, 그 정체는 Row Source의 `pr=`·`time=`으로 특정 노드를 지목해야 드러납니다.
3. 병목 노드는 cr·pr·time이 가장 큰 곳 — 여기서는 컨테이너반출입 Full Scan(cr 94.4%, pr 95.5%, time 66.5초)입니다.
4. `pw=0`은 해시 영역 스필이 없다는 신호 — PGA 부족을 원인으로 오귀속하지 않도록 반드시 확인합니다.
5. **높은 BCHR이 곧 효율은 아닙니다.** 92%가 높아 보여도 논리 읽기 250만 블록 자체가 과다하면 캐시를 키워도 낭비는 남습니다.

📌 한 줄 정리: BCHR 92%와 CPU 12.5%까지 옳게 읽어도, cr·pr·time이 모두 컨테이너반출입 Full Scan에 몰리고 pw=0인 사실을 놓치면 병목을 CPU·선박 인덱스·PGA 스필로 오귀속하게 됩니다.
