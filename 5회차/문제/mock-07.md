## 문제 7

### 문제

설비 점검 시스템의 점검이력 테이블(약 1,000만 건, 세그먼트 약 100,000 블록)에서 `점검이력_IX` 인덱스를 경유해 특정 기간의 점검 내역을 조회한 SQL의 트레이스이다. 이 트레이스에 대한 옳은 진단은?

(단, 옵티마이저 통계는 최신이고 인덱스는 Unusable 상태가 아니며, 이 SQL의 SELECT 목록은 `점검일자`, `점검결과` 두 컬럼뿐이다.)

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.005         0.005        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch       3001     5.395        37.995    60000    271800         0    600000
--------------------------------------------------------------------------------
Total       3003     5.400        38.000    60000    271800         0    600000

Rows       Row Source Operation
--------------------------------------------------------------------------------
 600000     TABLE ACCESS BY INDEX ROWID 점검이력 (cr=271800 pr=60000 pw=0
            time=37600000 us)
 600000       INDEX RANGE SCAN 점검이력_IX (cr=1800 pr=300 pw=0 time=620000 us)
```

### 선택지

① Disk 60,000이 Query 271,800의 약 22%로 BCHR이 약 78%에 그치고, Elapsed 38.0초에서 CPU 5.395초를 뺀 약 32.6초가 물리 읽기 대기이므로 버퍼 캐시 부족이 근본 원인이다. 인덱스는 cr=1,800·pr=300으로 이미 캐시에 잘 얹혀 있고 테이블 액세스 노드만 pr=60,000을 겪었으니, 캐시를 키워 점검이력 10만 블록을 상주시키면 이 SQL은 해결된다.

② 테이블 액세스 cr 271,800이 세그먼트 블록 수 100,000을 두 배 넘게 웃돌아 인덱스 손익분기점을 이미 넘겼으므로 Full Scan 전환만이 유일한 해법이다. 점검이력이 1,000만 건·10만 블록으로 커서 인덱스를 더 얹어 봐야 리프가 두꺼워질 뿐, 커버링 인덱스로는 이 38초를 개선할 수 없다.

③ 테이블 랜덤 블록 270,000을 ROWID 600,000으로 나눈 값이 약 0.45로 1보다 작으니 한 블록에서 여러 행을 뽑아 온 셈이라 클러스터링 팩터는 오히려 우수하다. 따라서 38초 대기의 정체는 테이블이 아니라 INDEX RANGE SCAN(cr=1,800, time=0.62초)이 겪은 인덱스 리프 블록 분할이다.

④ 테이블 랜덤 액세스가 ROWID 60만 건에 블록 I/O 27만을 써 CF가 테이블 블록 수(100,000)의 약 45배로 나쁘고, 그 랜덤 블록이 cr의 대부분이다. SELECT가 두 컬럼뿐이라 커버링 인덱스로 TABLE ACCESS BY INDEX ROWID를 없애면 cr이 인덱스 1,800에서 리프가 넓어져도 수천 블록대라 Full Scan(100,000)보다 유리하다.

---

### 정답 — ④

### 왜 ④인가

트레이스의 **세 숫자**를 나란히 놓습니다.

```text
600,000  ← 인덱스에서 얻은 ROWID 수 (INDEX RANGE SCAN 의 Rows)
271,800  ← 테이블 액세스 누적 블록 I/O (TABLE ACCESS 의 cr)
  1,800  ← 인덱스 스캔에 든 블록 (INDEX RANGE SCAN 의 cr)
```

부모(TABLE ACCESS) cr에는 자식(INDEX) cr이 누적돼 있으므로, **순수 테이블 랜덤 블록**을 분리합니다.

```text
테이블 랜덤 블록 = 271,800 − 1,800 = 270,000
랜덤 블록 비중   = 270,000 / 271,800 ≈ 99.3%    ← cr의 거의 전부가 테이블 랜덤
```

**클러스터링 팩터(CF)**의 밀도를 봅니다. 테이블의 행 밀도는 10,000,000 / 100,000 = 100행/블록입니다.

```text
CF 밀도 ≈ 테이블 랜덤 블록 ÷ ROWID 수 = 270,000 / 600,000 = 0.45  (ROWID당 블록)
CF 추정 ≈ 0.45 × 10,000,000 = 4,500,000
       → 테이블 블록 100,000의 약 45배 (100행/블록 × 0.45)
       → 나쁘지만 최악(1.0)은 아닌 중간값
```

읽은 행 비율은 600,000 / 10,000,000 = 6.0%로 흔히 '인덱스가 유리'로 보이는 범위지만, 나쁜 CF 탓에 **단일블록 랜덤 읽기가 27만 블록**에 이릅니다. 이제 세 경로를 **손익분기점**으로 비교합니다.

```text
현재 경로(인덱스+테이블) = 270,000(랜덤) + 1,800(인덱스) = 271,800 블록
Full Scan               = 100,000 블록 (multiblock)
커버링 인덱스 스캔       ≈ 인덱스만 읽음 → 컬럼 2개 추가로 리프가 넓어져도 수천 블록대
```

Elapsed 38.0초 대비 CPU 5.4초의 약 32.6초 간극은 물리 읽기(Disk 60,000) 대기이며, 그 뿌리는 테이블 랜덤 액세스입니다. SELECT가 `점검일자·점검결과` 두 컬럼뿐이므로 이 둘을 인덱스에 얹은 **커버링 인덱스**면 `TABLE ACCESS BY INDEX ROWID`가 사라져 랜덤 블록 27만이 통째로 없어집니다. cr은 인덱스만 읽는 수준으로 떨어져 Full Scan 100,000보다도 적습니다. 병목은 인덱스가 아니라 **테이블 랜덤 액세스**이고, 최적 처방은 **테이블 액세스 제거(커버링)**이므로 ④가 옳습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | (271,800−60,000)/271,800 ≈ 77.9%도, 38.0−5.395 ≈ 32.6초가 대기라는 것도 맞습니다. 그러나 낭비의 정체는 캐시 크기가 아니라 논리 읽기 271,800 자체(나쁜 CF)입니다. 캐시를 키워 pr 60,000을 0으로 만들어도 27만 블록의 랜덤 액세스와 그 CPU·래치 비용은 그대로 남으므로 근본 원인 오귀속입니다 |
| ② | ✗ | 271,800 > 100,000으로 손익분기점을 넘었다는 앞부분은 맞지만, 뒷부분의 단정이 틀립니다. SELECT가 `점검일자`·`점검결과` 두 컬럼뿐이라 커버링 인덱스가 TABLE ACCESS BY INDEX ROWID를 통째로 없애 cr을 현재 인덱스 cr 1,800 수준에서 리프가 넓어진 만큼만 늘어난 수천 블록대로 낮추므로, Full Scan 100,000보다 오히려 유리한 선택지가 남아 있습니다 |
| ③ | ✗ | 270,000/600,000 = 0.45라는 계산 자체는 맞으나 해석이 반대입니다. 100행/블록인 테이블에서 ROWID당 0.45블록은 CF가 테이블 블록의 약 45배라는 뜻으로 나쁜 쪽입니다. 인덱스 노드는 cr=1,800·time=0.62초뿐이라 38초를 만들 수 없고, 대기의 정체는 테이블 랜덤 액세스의 물리 I/O입니다 |
| ④ | **○** | 테이블 랜덤 블록 270,000 / ROWID 600,000 = 0.45로 CF는 테이블 블록의 약 45배(나쁨)이고 cr의 99.3%가 랜덤입니다. 두 컬럼만 읽으므로 커버링으로 테이블 액세스를 없애면 cr이 현재 인덱스 cr 1,800 수준에서 리프가 넓어진 만큼 늘어도 수천 블록대에 그쳐 Full Scan 100,000보다 유리합니다 |

---

## ✅ 이 문제의 핵심

1. **테이블 랜덤 블록 = TABLE ACCESS cr − INDEX cr** = 271,800 − 1,800 = 270,000. 부모 cr에는 자식 인덱스 cr이 누적돼 있으니 반드시 빼서 분리합니다.
2. **CF 밀도 ≈ 테이블 랜덤 블록 ÷ ROWID 수.** 0.45는 100행/블록 기준 테이블 블록의 약 45배로, 최악(1.0)은 아니어도 분명히 나쁜 값입니다.
3. cr의 99.3%가 테이블 랜덤이므로 병목은 인덱스가 아니라 **테이블 랜덤 액세스**입니다.
4. **손익분기점 비교**: 현재 271,800 > Full Scan 100,000 > 커버링 수천 블록대(현재 인덱스 cr 1,800에서 리프가 넓어진 만큼 증가). 읽는 컬럼이 적으면 Full Scan보다 커버링이 더 유리합니다.
5. **높은 논리 읽기 자체가 낭비**라면 캐시 확대로는 해결되지 않습니다 — 테이블 액세스를 제거(커버링)해야 랜덤 블록 27만이 사라집니다.

📌 한 줄 정리: ROWID 60만에 테이블 랜덤 27만이면 CF는 테이블 블록의 약 45배로 나쁘고, SELECT가 두 컬럼뿐이라 커버링 인덱스로 테이블 액세스를 없애는 것이 Full Scan보다도 유리한 처방입니다.
