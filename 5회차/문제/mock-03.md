## 문제 3

### 문제

전자결재 시스템의 야간 배치가 결재 대기 문서 약 8,000건을 처리하면서, 문서마다 문서번호를 문자열 리터럴로 이어붙여(`WHERE 문서번호 = 'DOC-2026-...'`) SQL을 새로 만들어 실행한다. 배치가 38초를 넘겨 느리다는 신고가 들어와 TKPROF를 수집했더니 아래처럼 비재귀(non-recursive)·재귀(recursive) 통계가 분리되어 출력됐다. 이 트레이스에 대한 옳은 진단은?

(단, 옵티마이저 통계는 최신이고 결재선·문서 테이블의 인덱스는 정상이며, 배치는 문서 1건당 리터럴 SQL 1종을 생성한다.)

#### [아 래]

```text
OVERALL TOTALS FOR ALL NON-RECURSIVE STATEMENTS

Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse       8000    27.000        31.000        0         0         0         0
Execute     8000     3.200         3.400        0     64000      8000      8000
Fetch       8000     1.800         4.100      400     96000         0      8000
--------------------------------------------------------------------------------
Total      24000    32.000        38.500      400    160000      8000     16000

OVERALL TOTALS FOR ALL RECURSIVE STATEMENTS

Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse      16000     6.000         6.200        0         0         0         0
Execute    48000     5.400         5.600      120    240000      4000    120000
Fetch      96000     4.600         4.900      800    320000         0    400000
--------------------------------------------------------------------------------
Total     160000    16.000        16.700      920    560000      4000    520000

Misses in library cache during parse: 8000
```

### 선택지

① 재귀 Execute가 48,000회로 비재귀 Execute 8,000회의 6배이고 재귀 Rows가 520,000행에 이르므로, 배치가 문서 한 건마다 상관 서브쿼리를 여러 번 돌려 행을 퍼올리는 데이터 처리 로직이 진짜 병목이다. 비재귀 Parse CPU 27초는 그 무거운 SQL의 계획을 세우느라 든 부수 비용이니, 서브쿼리를 조인으로 재작성해 재귀 Query 560,000 블록을 걷어내면 38.5초가 해소된다.

② 재귀 Fetch Disk 800을 포함해 재귀 Disk가 920으로 비재귀 Disk 400의 2배가 넘고 재귀 Query도 560,000 블록에 달하니, 파싱이 아니라 데이터 딕셔너리 블록을 매번 물리적으로 다시 읽는 것이 정체 원인이다. 버퍼 캐시를 키워 재귀 블록 I/O를 메모리에 상주시키면 재귀 Elapsed 16.7초가 줄어 배치 38.5초도 함께 짧아진다.

③ 비재귀 Parse CPU 27초는 옵티마이저가 문서 8,000건 각각에 맞는 실행계획을 정교하게 최적화하느라 쓴 정상 비용이고, 그 덕에 비재귀 Execute CPU 3.2초·Fetch CPU 1.8초로 실행이 억제되었다. 재귀 Call 160,000회 역시 그 좋은 계획을 실행하며 딕셔너리를 참조한 결과이므로, Elapsed 38.5초는 8,000건 처리의 합당한 값이고 현재 상태가 이미 최적이다.

④ 비재귀 Parse CPU 27초가 가리키듯 리터럴 SQL의 하드파싱이 주범이고, 재귀 Parse 16,000·재귀 Call 160,000은 그 하드파싱이 파싱 중 데이터 딕셔너리를 조회하며 파생시킨 파싱 부하이지 애플리케이션 데이터 로직이 무거워서가 아니다. 바인드 변수로 하드파싱을 없애면 재귀 딕셔너리 호출도 함께 줄어든다.

---

### 정답 — ④

### 왜 ④인가

먼저 **Call 통계**에서 비재귀 CPU의 정체가 어디인지 봅니다.

```text
비재귀 Total = Parse + Execute + Fetch
  Count :  8000 + 8000 + 8000 = 24000
  CPU   : 27.000 + 3.200 + 1.800 = 32.000
비재귀 Parse CPU 비중 = 27.000 / 32.000 × 100 ≈ 84.4%   ← 비재귀 CPU의 대부분이 파싱
파스 1회당 CPU = 27.000 / 8,000 ≈ 3.4 ms   (소프트파싱은 보통 0.1ms 미만)
```

비재귀 CPU 32초 중 27초가 **Parse**입니다. 파스 1회에 3.4ms는 소프트파싱(공유 커서 탐색, 0.1ms 미만) 수준을 크게 넘어 **하드파싱**의 값입니다. `Misses in library cache during parse: 8000`이 파스 8,000회가 전부 캐시 미스, 즉 하드파싱임을 확정합니다.

```text
하드파싱 비율 = 라이브러리 캐시 미스 ÷ 비재귀 Parse Count
             = 8,000 / 8,000 = 100%   ← 리터럴 SQL이라 매 문서가 새 커서
```

다음은 **재귀 통계가 무엇인지**입니다. 재귀 Call은 애플리케이션 SQL이 아니라, 오라클이 파싱·공간 관리 중에 **데이터 딕셔너리를 조회하려고 내부적으로 실행한 SQL**입니다. 하드파싱 1회마다 obj\$·col\$ 같은 딕셔너리를 훑으므로, 하드파싱이 많을수록 재귀 호출이 함께 부풀어 오릅니다.

```text
재귀/비재귀 Call 비율 = 재귀 Total Count ÷ 비재귀 Total Count
                      = 160,000 / 24,000 ≈ 6.67배
재귀 Parse ÷ 비재귀 Parse = 16,000 / 8,000 = 2.0배
재귀 Query 1회당 ≈ 560,000 / 16,000 = 35 블록/파스   ← 파스마다 딕셔너리 재조회
```

핵심은 **두 축이 별개**라는 점입니다.

```text
축 A — 파싱 부하 : 리터럴 SQL → 하드파싱(Parse CPU 27s, 미스 8,000)
                  → 파싱 중 딕셔너리 재귀 SQL(재귀 Call 160,000) 파생
축 B — 데이터 처리량 : 배치가 실제로 다루는 문서 8,000건(비재귀 Execute Rows 8,000)

재귀 통계의 큰 숫자(Rows 520,000·Query 560,000)는 축 A(파싱 부하)의 부산물이지
축 B(애플리케이션 데이터 로직)가 무거워서가 아님.
```

재귀 Query 560,000·재귀 Rows 520,000이 커 보여도 이것은 딕셔너리 조회의 흔적이지, 배치가 처리한 데이터(문서 8,000건)의 양과는 별개입니다. 바인드 변수로 SQL 문자열을 한 종으로 통일하면 하드파싱(축 A)이 사라지고, 그 파생물인 재귀 딕셔너리 호출도 함께 붕괴합니다. 따라서 파싱 부하와 데이터 처리량을 구분해 진단한 ④가 옳습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | 재귀 Execute 48,000·재귀 Rows 520,000은 참이지만 그 정체는 상관 서브쿼리 실행이 아니라 하드파싱 8,000회가 파싱 중 훑은 딕셔너리 조회입니다. 배치가 실제로 다룬 데이터는 비재귀 Execute Rows 8,000(문서 8,000건)뿐이라 데이터 로직은 가볍고, Parse CPU 27초를 '부수 비용'으로 밀어낸 것이 곧 파싱 부하를 데이터 로직으로 오귀속한 별개 축 혼동입니다 |
| ② | ✗ | 재귀 Disk 920(Fetch 800)·비재귀 Disk 400은 참이나, 920 블록의 물리 읽기로 재귀 Elapsed 16.7초를 만들 수는 없습니다. 재귀 Query 560,000은 파스 16,000회가 파스당 약 35블록씩 딕셔너리를 재조회한 흔적이므로, 정체 원인은 버퍼 캐시 미스가 아니라 미스 8,000이 확정하는 하드파싱 자체이고 캐시 확대는 헛짚은 처방입니다 |
| ③ | ✗ | 비재귀 Execute CPU 3.2초·Fetch CPU 1.8초가 작은 것은 데이터 처리가 원래 가벼웠다는 뜻이지 정교한 최적화의 대가가 아닙니다. `Misses in library cache during parse: 8000`이 파스 8,000회 전부가 하드파싱(파스당 3.4ms)임을 확정하므로 27초는 정상 비용이 아닌 낭비이고, 재귀 Call도 계획 실행이 아니라 그 하드파싱의 딕셔너리 파생 부하라 '이미 최적'은 성립하지 않습니다 |
| ④ | **○** | Parse CPU 27초가 비재귀 CPU의 84%(파스당 3.4ms)에 미스 8,000으로 하드파싱이 주범이고, 재귀 Parse 16,000·Call 160,000은 그 하드파싱의 딕셔너리 파생 부하입니다. 파싱 부하와 데이터 처리량을 별개 축으로 옳게 분리해, 바인드 변수가 재귀까지 줄인다고 진단했습니다 |

---

## ✅ 이 문제의 핵심

1. **하드파싱 비율 = `Misses in library cache during parse` ÷ 비재귀 Parse Count** = 8,000/8,000 = 100%. 파스당 CPU 3.4ms도 소프트파싱(0.1ms 미만)을 크게 넘어 하드파싱을 뒷받침합니다.
2. **재귀(recursive) 통계는 애플리케이션 SQL이 아니라 파싱·딕셔너리 내부 SQL입니다.** 하드파싱이 많으면 파싱 중 딕셔너리 조회로 재귀 호출이 함께 부풀어 오릅니다(재귀/비재귀 Call ≈ 6.67배).
3. **파싱 부하(축 A)와 데이터 처리량(축 B)은 별개입니다.** 재귀 Query 560,000·Rows 520,000이 커도 이는 딕셔너리 부산물이지, 배치가 다룬 문서 8,000건(비재귀 Execute Rows)과 무관합니다.
4. 처방은 서브쿼리 재작성·버퍼 캐시가 아니라 **바인드 변수**입니다. 하드파싱을 없애면 그 파생물인 재귀 딕셔너리 호출도 함께 감소합니다.

📌 한 줄 정리: 비재귀 Parse CPU 27초(파스당 3.4ms·미스 8,000)가 하드파싱을 가리키고, 재귀 Call 160,000은 그 하드파싱의 딕셔너리 파생 부하이므로, 재귀 통계의 큰 숫자를 데이터 로직 과부하로 오독하지 말고 파싱 부하와 데이터 처리량을 별개 축으로 봐야 합니다.
