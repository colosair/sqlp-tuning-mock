## 문제 4

### 문제

옵티마이저가 실행 전에 추정하는 예상 실행계획과, 실제로 수행된 실행계획을 확인하는 방법, 그리고 계획을 고정해 안정성을 확보하는 수단(SQL Plan Baseline·Stored Outline)에 대한 설명으로 가장 적절한 것은?

### 선택지

① EXPLAIN PLAN이나 DBMS_XPLAN.DISPLAY로 보는 것은 옵티마이저가 실행 전에 추정한 예상 계획이라 바인드 값이나 실제 데이터 분포에 따라 실행 시점의 계획과 달라질 수 있으므로, 실제로 수행된 계획은 DBMS_XPLAN.DISPLAY_CURSOR로 커서 캐시에서 확인해야 정확하다.

② SQL Plan Baseline이나 Stored Outline을 적용하면 옵티마이저가 예상 계획을 산출하는 과정 자체가 생략되고 등록된 계획을 그대로 꺼내 쓰므로, 하드파싱은 물론 후보 계획을 고르는 옵티마이징 비용까지 사라지고 DISPLAY로 뽑은 예상 계획이 실행 시점 계획과 어긋날 여지도 없어진다.

③ EXPLAIN PLAN은 대상 SQL을 실제로 한 번 수행하면서 각 단계를 거친 실제 처리 건수와 소요 시간을 측정해 PLAN_TABLE에 적재하고 DBMS_XPLAN.DISPLAY가 그 행을 읽어 보여 주므로, 여기서 얻은 계획은 바인드 값이 달라지더라도 실행 시점의 실제 계획과 그대로 일치한다.

④ DBMS_XPLAN.DISPLAY_CURSOR는 커서 캐시에 올라온 계획을 보여 주는 것은 물론 아직 실행되지 않아 커서가 없는 SQL도 SQL_ID나 SQL 텍스트만 넘기면 옵티마이저를 불러 예상 계획을 산출해 주므로, EXPLAIN PLAN과 PLAN_TABLE을 거치지 않고도 실행 전 계획 확인이 가능하다.

---

### 정답 — ①

### 왜 ①인가

'예상 계획을 뽑는 도구'와 '실제 수행된 계획을 보는 도구'의 경계를 흐리지 않고 갈라야 합니다.

```text
예상 계획(추정)         : EXPLAIN PLAN → PLAN_TABLE, DBMS_XPLAN.DISPLAY
                          - SQL을 실행하지 않고 옵티마이저가 산출한 계획
                          - 바인드 값·데이터 분포에 따라 실제와 달라질 수 있음
실제 계획(수행됨)        : DBMS_XPLAN.DISPLAY_CURSOR
                          - 이미 실행되어 커서 캐시(라이브러리 캐시)에 올라온 계획을 조회
계획 안정성(고정)        : SQL Plan Baseline / Stored Outline
                          - 계획 '선택'을 제약할 뿐, 파싱·최적화 과정을 없애지는 않음
```

EXPLAIN PLAN·DISPLAY로 보는 것은 옵티마이저가 실행 전에 추정한 예상 계획입니다. 바인드 변수 값이나 실제 데이터 분포에 따라 실행 시점의 계획이 달라질 수 있으므로, 실제로 무엇이 수행됐는지는 커서 캐시에 올라온 계획을 DISPLAY_CURSOR로 확인해야 정확합니다. ①은 두 도구의 경계를 바르게 나눴습니다.

②는 계획을 고정하는 것과 최적화를 생략하는 것을 뒤섞었습니다. Baseline·Outline은 옵티마이저가 고를 수 있는 계획을 제약할 뿐, 파싱과 계획 평가 과정 자체를 없애지 않으며 등록된 계획이 검증에서 탈락하면 다른 계획이 쓰이므로 "어긋날 여지가 없다"고 할 수도 없습니다. ③은 EXPLAIN PLAN이 SQL을 실제로 실행한다고 오해했습니다. EXPLAIN PLAN은 수행 없이 추정만 하므로 실제 처리 건수·소요 시간을 측정하지 않고, PLAN_TABLE에 담기는 값도 추정치이며 그 계획이 실제와 일치한다는 보장도 없습니다. ④는 DISPLAY_CURSOR가 커서 캐시에 올라온(=이미 실행된) 계획을 읽는 도구라는 경계를 무시했습니다. SQL_ID로 커서를 찾는 방식이라 실행되지 않아 커서가 없는 SQL은 애초에 조회 대상이 되지 않습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | DISPLAY로 보는 것은 실행 전 예상 계획이라 실제와 달라질 수 있고, 실제 수행된 계획은 커서 캐시를 읽는 DISPLAY_CURSOR로 확인해야 정확합니다 |
| ② | ✗ | Baseline·Outline은 계획 '선택'을 제약할 뿐이라 파싱과 계획 평가는 그대로 일어나고, 등록 계획을 꺼내 쓴다고 해서 옵티마이징 비용이 사라지지도 예상 계획과 실제 계획의 괴리가 없어지지도 않습니다 |
| ③ | ✗ | EXPLAIN PLAN은 SQL을 실행하지 않고 추정만 하므로 실제 처리 건수도 소요 시간도 측정하지 않습니다. PLAN_TABLE에 적재되는 값은 추정치이고, 바인드 값이 달라지면 실행 시점 계획과 어긋날 수 있습니다 |
| ④ | ✗ | DISPLAY_CURSOR는 SQL_ID로 커서 캐시를 찾아 이미 실행된 계획을 읽는 도구입니다. 커서가 없는 SQL은 조회 대상 자체가 없으므로, 실행 전 예상 계획은 EXPLAIN PLAN·PLAN_TABLE 쪽으로 가야 합니다 |

---

## ✅ 이 문제의 핵심

1. **EXPLAIN PLAN·DISPLAY**는 실행 전 **예상 계획**을 추정해 보여 줄 뿐, 실행하지 않습니다.
2. **실제 수행된 계획**은 커서 캐시를 읽는 **DISPLAY_CURSOR**로 확인해야 정확합니다.
3. 예상 계획은 바인드 값·데이터 분포에 따라 **실제 계획과 달라질 수 있습니다**.
4. **SQL Plan Baseline·Stored Outline**은 계획 선택을 고정할 뿐 파싱·최적화 과정을 없애지 않습니다.

📌 한 줄 정리: DISPLAY는 실행 전 예상 계획, DISPLAY_CURSOR는 커서 캐시의 실제 계획을 보는 도구이며(①), 계획 고정 수단이 최적화를 생략한다거나 EXPLAIN PLAN이 SQL을 실행한다는 서술은 도구의 경계를 흐린 것입니다.
