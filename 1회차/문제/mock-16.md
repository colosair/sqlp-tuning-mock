## 문제 16

### 문제

매출 테이블은 매출일자(DATE 타입)를 기준으로 월별 RANGE 파티셔닝되어 있다(아래 DDL). 각 선택지는 `SELECT SUM(매출금액) FROM 매출 WHERE …`의 WHERE 절이다. Partition Pruning이 효과적으로 작동하여 필요한 파티션만 읽는 것으로 보기 **가장 적절하지 <u>않은</u> 것은?**

#### [아 래]

```sql
CREATE TABLE 매출 (
    매출번호   NUMBER,
    매출일자   DATE,
    매출금액   NUMBER,
    지점코드   VARCHAR2(4)
)
PARTITION BY RANGE (매출일자) (
    PARTITION p_202601 VALUES LESS THAN (DATE '2026-02-01'),
    PARTITION p_202602 VALUES LESS THAN (DATE '2026-03-01'),
    PARTITION p_202603 VALUES LESS THAN (DATE '2026-04-01'),
    PARTITION p_202604 VALUES LESS THAN (DATE '2026-05-01'),
    PARTITION p_202605 VALUES LESS THAN (DATE '2026-06-01'),
    PARTITION p_202606 VALUES LESS THAN (DATE '2026-07-01'),
    PARTITION p_max    VALUES LESS THAN (MAXVALUE)
);
```

### 선택지

① `WHERE 매출일자 >= DATE '2026-03-01' AND 매출일자 < DATE '2026-04-01'`

② `WHERE 매출일자 BETWEEN DATE '2026-02-01' AND DATE '2026-02-28'`

③ `WHERE 매출일자 >= DATE '2026-05-01' AND 매출일자 < DATE '2026-07-01'`

④ `WHERE TO_CHAR(매출일자, 'YYYYMM') = '202603'`

---

### 정답 — ④

### 왜 ④인가

Partition Pruning은 옵티마이저가 **WHERE 조건의 값을 파티션 경계(VALUES LESS THAN)와 대조**해 스캔 대상 파티션을 미리 좁히는 최적화입니다. 이 대조가 가능하려면 조건이 **파티션 키 칼럼(매출일자) 자체**에 직접 걸려 있어야 합니다.

```text
① 매출일자 ∈ [2026-03-01, 2026-04-01)   → p_202603 한 개
② 매출일자 ∈ [2026-02-01, 2026-02-28]   → p_202602 한 개
③ 매출일자 ∈ [2026-05-01, 2026-07-01)   → p_202605, p_202606 두 개
④ TO_CHAR(매출일자,'YYYYMM') = '202603'  → 키에 함수, 경계 대조 불가
```

①②③은 모두 매출일자를 **가공하지 않은 날짜 범위**로 걸었으므로, 옵티마이저가 경계와 대조해 해당 파티션만 접근합니다(③은 경계상 두 파티션이지만 여전히 나머지는 건너뜁니다 — Pruning 작동).

④는 `TO_CHAR(매출일자, …)`로 **파티션 키에 형변환 함수를 씌웠습니다.** 그러면 옵티마이저는 함수 결과값을 파티션 경계와 대조할 수 없어 Pruning을 포기하고, `p_202601 … p_max` **모든 파티션을 스캔**한 뒤 각 행에서 TO_CHAR를 평가해 필터합니다. 조건이 의미상 "2026년 3월"을 겨냥하는 부분적 진실이라도, 형변환 한 줄이 최선(1개 파티션)을 최악(전 파티션 스캔)으로 뒤집습니다. 그래서 Pruning이 효과적으로 작동한다고 볼 수 없는 것은 ④입니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ○ | 매출일자를 가공 없이 `[2026-03-01, 2026-04-01)` 범위로 걸어 p_202603 한 개로 정확히 Pruning됩니다 |
| ② | ○ | BETWEEN 구간이 2026-02 경계 안에 들어가 p_202602 한 개만 접근합니다. Pruning 작동합니다 |
| ③ | ○ | 두 달 범위라 p_202605·p_202606 두 파티션을 읽지만, 나머지 파티션은 건너뛰므로 Pruning은 여전히 작동합니다 |
| ④ | **✗** | 파티션 키에 `TO_CHAR`를 씌워 경계 대조가 불가능해집니다. 전 파티션을 스캔한 뒤 필터하므로 Pruning이 깨집니다 |

---

## ✅ 이 문제의 핵심

1. **Partition Pruning은 파티션 키 칼럼에 직접 걸린 조건에서만 작동**합니다. 키를 가공하면 경계와 대조할 수 없습니다.
2. **날짜 범위 조건(>=, <, BETWEEN)은 경계와 그대로 대조**되어 필요한 파티션만 남깁니다.
3. **여러 파티션에 걸치더라도(③) Pruning은 유효**합니다 — 나머지 파티션을 건너뛰기만 하면 됩니다.
4. **`TO_CHAR`·`TRUNC` 등 키 가공은 Pruning을 무력화**해 전 파티션 스캔을 유발합니다. "월만 뽑았다"는 부분적 타당함이 함정입니다.

📌 한 줄 정리: 파티션 키를 가공하지 않은 날짜 범위는 Pruning이 작동하지만, `TO_CHAR(매출일자,…)`처럼 키에 형변환을 씌우면 경계 대조가 불가능해져 전 파티션을 스캔합니다.
