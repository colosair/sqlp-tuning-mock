## 문제 20

### 문제

재고 테이블의 상품 'P-01' 행(초기 재고수량 = 500)을 두 트랜잭션이 아래 순서로 접근한다. t2에서 TX2가 수행한 `SELECT`가 반환하는 재고수량을 **오라클과 SQL Server에서 순서대로** 나열한 것으로 적절한 것은? (단, 두 DBMS 모두 기본 격리수준을 조정하지 않았고, SQL Server는 READ_COMMITTED_SNAPSHOT(RCSI)을 사용하지 않는다.)

#### [아 래]

```text
시각   TX1                                          TX2
----   ------------------------------------------   ---------------------------------
t1     UPDATE 재고 SET 재고수량 = 재고수량 - 120
       WHERE 상품코드 = 'P-01';   (500 → 380, 미커밋)
t2                                                  SELECT 재고수량 FROM 재고
                                                    WHERE 상품코드 = 'P-01';
t3     COMMIT;
t4                                                  COMMIT;

초기 재고수량 = 500
```

### 선택지

① 오라클 380, SQL Server 500
② 오라클 500, SQL Server 500
③ 오라클 380, SQL Server 380
④ 오라클 500, SQL Server 380

---

### 정답 — ④

### 왜 ④인가

두 DBMS의 기본 격리수준은 모두 **READ COMMITTED**로 같지만, "읽기가 쓰기를 만났을 때"의 처리 방식이 다릅니다. 오라클은 MVCC(다중 버전)로 읽고, 기본 SQL Server는 공유 잠금(locking)으로 읽습니다.

```text
[오라클] — MVCC, 읽기는 쓰기를 기다리지 않음
  t1: TX1이 500 → 380 갱신(미커밋). 변경 전 이미지 500이 언두에 보존됨
  t2: TX2의 SELECT는 t2 시점에 '커밋된' 값을 Undo로 재구성해 즉시 반환
      → TX1의 미커밋 380은 보이지 않음 → 반환값 = 500
  결과(오라클) = 500

[SQL Server] — 기본 RC(잠금 기반), RCSI 미사용
  t1: TX1이 380으로 갱신하며 해당 행에 배타(X) 락 보유(미커밋)
  t2: TX2의 SELECT는 공유(S) 락을 얻으려다 X 락과 비호환 → 대기(블로킹)
  t3: TX1이 COMMIT → 380 확정 → X 락 해제 → TX2의 SELECT가 그제야 진행
      → 반환값 = 380
  결과(SQL Server) = 380
```

핵심 차이는 **오라클은 읽기가 쓰기를 기다리지 않고(비블로킹) 커밋된 이전 값 500을 보고**, **기본 SQL Server는 미커밋 X 락에 막혀 대기했다가 커밋 후 값 380을 본다**는 점입니다. 따라서 (오라클, SQL Server) = (500, 380), 정답은 ④입니다.

RCSI를 켰다면 SQL Server도 스냅샷으로 500을 읽어 두 값이 같아지지만, 발문의 `(단, … RCSI를 사용하지 않는다)` 조건이 이 경로를 차단합니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | 두 값을 서로 뒤바꾼 것입니다. 비블로킹으로 500을 읽는 쪽이 오라클이고, 대기 후 380을 읽는 쪽이 SQL Server입니다 |
| ② | ✗ | SQL Server를 오라클처럼 취급했습니다. 기본 RC(RCSI 미사용)에서 SELECT는 X 락에 막혀 대기하므로 500이 아니라 380입니다 |
| ③ | ✗ | 오라클을 SQL Server처럼 취급했습니다. 오라클은 MVCC로 커밋된 이전 값 500을 즉시 읽으므로 380이 아닙니다 |
| ④ | **○** | 오라클은 MVCC로 미커밋 변경을 건너뛰고 500, 기본 SQL Server는 X 락에 블로킹됐다가 커밋 후 380을 읽습니다 |

---

## ✅ 이 문제의 핵심

1. **기본 격리수준은 둘 다 READ COMMITTED**지만, 구현이 다릅니다 — 오라클은 MVCC, 기본 SQL Server는 잠금 기반입니다.
2. **오라클: 읽기가 쓰기를 막지 않음.** 미커밋 변경은 언두로 되돌린 커밋 값(500)을 비블로킹으로 읽습니다.
3. **기본 SQL Server: 읽기가 미커밋 쓰기에 블로킹.** SELECT가 공유 락을 얻으려다 대기하고, 커밋 후의 값(380)을 읽습니다.
4. **RCSI(READ_COMMITTED_SNAPSHOT)를 켜면** SQL Server도 스냅샷으로 500을 읽어 오라클과 같아집니다 — 발문의 차단 조건이 이 예외를 막습니다.

📌 한 줄 정리: 같은 READ COMMITTED라도 오라클은 MVCC로 커밋된 이전 값 500을 비블로킹으로 읽고, RCSI를 끈 SQL Server는 X 락에 막혔다가 커밋 후 값 380을 읽습니다.
