## 문제 19

### 문제

SQL Server에서 계좌 테이블을 갱신하는 두 세션(53, 57)이 동시에 수행되던 중, `sys.dm_tran_locks`를 조회한 결과이다. 이 락 상태에 대한 해석으로 가장 적절한 것은?

#### [아 래]

```text
resource_type  request_mode  request_status  session_id  resource_description
-----------------------------------------------------------------------------
OBJECT         IX            GRANT           53          계좌
OBJECT         IX            GRANT           57          계좌
PAGE           IX            GRANT           53          1:8842
PAGE           IX            GRANT           57          1:8842
KEY            X             GRANT           53          (계좌번호=100-2277)
KEY            X             WAIT            57          (계좌번호=100-2277)
```

### 선택지

① 세션 57이 세션 53에 블로킹되어 있고, 판별 근거는 동일 KEY 자원(계좌번호=100-2277)에 대한 57의 X 요청이 WAIT이기 때문이다.
② 세션 53이 세션 57을 기다리고 있으며, 이 상황의 피해자(blocked)는 세션 53이다.
③ 세션 53과 57은 OBJECT 수준에서 IX 락을 함께 보유하므로 상호 블로킹(교착) 상태에 있다.
④ 세션 57의 대기는 PAGE(1:8842) 자원 경합 때문이며, 두 세션은 서로를 기다리는 교착상태(deadlock)다.

---

### 정답 — ①

### 왜 ①인가

블로킹을 판별하는 자리는 **동일한 자원(resource)에 대해 한쪽은 GRANT, 다른 쪽은 WAIT인 행**입니다. 표를 자원별로 갈라 보면 답이 한 곳에서만 나옵니다.

```text
자원                          53의 상태     57의 상태     호환 여부
-----------------------------------------------------------------
OBJECT 계좌 (IX / IX)         GRANT         GRANT         IX↔IX 호환 → 대기 없음
PAGE 1:8842 (IX / IX)         GRANT         GRANT         IX↔IX 호환 → 대기 없음
KEY 100-2277 (X / X)          GRANT         WAIT          X↔X 비호환 → 여기서 대기
```

- OBJECT와 PAGE의 IX(Intent Exclusive)는 **서로 호환**됩니다. 두 세션이 같은 테이블·페이지에 IX를 나란히 GRANT받은 것은 정상이며 블로킹의 근거가 아닙니다.
- 실제 충돌은 **KEY 자원**에서 일어납니다. 세션 53이 계좌번호 100-2277 행에 X 락을 GRANT로 잡았고, 세션 57이 같은 키에 X를 요청했으나 status가 **WAIT**입니다. X↔X는 비호환이므로 57은 53의 커밋/롤백을 기다립니다.

따라서 **블로커는 53, 피해자는 57**이고, 그 근거는 IX가 아니라 KEY 행의 WAIT 상태입니다. ①이 방향과 근거를 모두 맞혔습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | KEY 100-2277에서 53은 X GRANT, 57은 X WAIT입니다. 동일 자원의 GRANT↔WAIT 쌍이 블로킹의 유일한 판별 근거이며, 57이 53에 막혀 있습니다 |
| ② | ✗ | 방향이 반대입니다. 세션 53의 세 행은 모두 GRANT여서 기다리는 쪽이 아닙니다. 대기(WAIT)는 57에만 있으므로 피해자는 57입니다 |
| ③ | ✗ | 두 세션이 함께 가진 OBJECT의 IX는 서로 호환되는 락입니다. 공통으로 보이는 IX를 블로킹 근거로 삼으면 안 됩니다 — 상호 블로킹이 아닙니다 |
| ④ | ✗ | PAGE 1:8842는 두 세션 모두 IX GRANT여서 경합이 없습니다. WAIT는 57 한쪽에만 있어 상호 대기(교착)도 아닙니다 |

---

## ✅ 이 문제의 핵심

1. **블로킹 판별은 request_status로** 합니다. 같은 자원 행에서 GRANT와 WAIT가 마주칠 때, WAIT 쪽이 GRANT 쪽에 막힌 것입니다.
2. **IX(Intent) 락끼리는 호환**됩니다. 여러 세션이 같은 OBJECT·PAGE에 IX를 함께 보유하는 것은 정상이며 블로킹 신호가 아닙니다.
3. 모두에게 공통으로 보이는 단서(둘 다 IX 보유)는 판별 근거가 될 수 없습니다 — 차이가 나는 지점(KEY의 X GRANT vs X WAIT)이 근거입니다.
4. 대기가 한쪽에만 있으면 단방향 블로킹이지 교착이 아닙니다. 교착은 양쪽 모두 WAIT일 때입니다.

📌 한 줄 정리: 공통으로 가진 IX가 아니라 동일 KEY 자원의 X GRANT(53) ↔ X WAIT(57) 쌍이 블로킹의 근거이며, 57이 53에 막혀 있습니다.
