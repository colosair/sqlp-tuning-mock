## 문제 4

### 문제

회원 테이블(약 1,800만 건)과 접속이력 테이블(약 240만 건)을 조인해 집계하는 SQL의 TKPROF 결과이다. 이 트레이스의 해석으로 가장 적절하지 <u>않은</u> 것은?

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.003         0.003        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch        121     3.147        28.600    72400    810300         0      1800
--------------------------------------------------------------------------------
Total        123     3.150        28.603    72400    810300         0      1800

Rows       Row Source Operation
--------------------------------------------------------------------------------
   1800     HASH JOIN  (cr=810300 pr=72400 pw=0 time=28551000 us)
2400000       TABLE ACCESS FULL 접속이력 (cr=72300 pr=12400 pw=0 time=1802000 us)
18000000      TABLE ACCESS FULL 회원 (cr=738000 pr=60000 pw=0 time=25640000 us)
```

### 선택지

① Elapsed Time(28.6초)과 CPU Time(3.15초)의 약 25.5초 간극은 대기 시간이며, 72,400개 디스크 블록의 물리 I/O 대기가 가장 유력한 원인이다.
② 이 실행의 BCHR은 약 91.1%로, 논리적 I/O 약 81만 블록 중 약 9%를 디스크에서 물리적으로 읽었다.
③ 두 Full Scan 중 회원 테이블(cr=738,000)이 전체 블록 I/O의 약 91%를 차지해 블록 소비의 주된 지점이다.
④ CPU Time이 3.15초로 집계됐으므로 이 SQL의 주된 병목은 CPU 연산이고, 인스턴스 CPU 자원 증설이 최우선 처방이다.

---

### 정답 — ④

### 왜 ④인가

④는 **수치는 맞지만 병목의 원인을 엉뚱한 곳에 갖다 붙인** 진술입니다(원인 오귀속). CPU Time이 3.15초인 것은 사실이지만, 전체 응답시간 28.6초 가운데 CPU가 차지하는 비중은 오히려 작습니다.

```text
Elapsed − CPU = 28.600 − 3.150 = 25.45초  ← 일한 시간이 아니라 '기다린' 시간
CPU 비중 = 3.150 / 28.600 × 100 ≈ 11.0%   ← 응답시간의 1/9 남짓
```

응답시간의 약 89%가 대기이고, 그 대기의 정체는 Row Source의 `time=` 값이 가리킵니다. 회원 테이블 Full Scan 한 노드에서만 25.64초(time=25640000 us)가 흘렀고 이 단계의 물리 읽기는 pr=60,000입니다. 즉 병목은 CPU가 아니라 **회원 테이블 Full Scan의 디스크 I/O**이므로, 처방은 CPU 증설이 아니라 인덱스·부분범위·집계 전략으로 Full Scan을 줄이는 것입니다. 따라서 ④가 적절하지 않습니다.

나머지 셋은 모두 옳습니다.

```text
① 대기 = Elapsed − CPU = 28.600 − 3.150 ≈ 25.45초
   물리 I/O Disk = 72,400 블록 → db file 읽기 대기가 유력  (참)

② BCHR = ((Query + Current) − Disk) / (Query + Current) × 100
        = (810,300 + 0 − 72,400) / 810,300 × 100
        = 737,900 / 810,300 × 100 ≈ 91.1%
   → 논리적 I/O 중 약 100 − 91.1 = 8.9% ≈ 9%를 디스크에서 읽음  (참)

③ 회원 cr 비중 = 738,000 / 810,300 × 100 ≈ 91.1%
   → 접속이력(72,300)보다 회원 Full Scan이 블록 소비의 주범  (참)
```

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ○ | Elapsed 28.6초 − CPU 3.15초 = 약 25.5초가 대기이고, Disk 72,400 블록의 물리 I/O 대기가 그 대기의 유력한 원인입니다 |
| ② | ○ | (810,300 − 72,400)/810,300 = 약 91.1%로 BCHR 계산이 정확하며, 나머지 약 9%가 디스크 물리 읽기입니다 |
| ③ | ○ | 회원 cr=738,000은 전체 810,300의 약 91%로, 접속이력(72,300)보다 압도적이어서 블록 소비의 주된 지점이 맞습니다 |
| ④ | **✗** | CPU 3.15초는 응답시간의 11%뿐입니다. 병목은 회원 Full Scan의 디스크 I/O(pr=60,000, time=25.6초)이지 CPU가 아니므로 CPU 증설은 원인 오귀속입니다 |

---

## ✅ 이 문제의 핵심

1. **CPU Time이 '측정됐다'는 사실과 'CPU가 병목이다'는 판정은 별개**입니다. 비중(3.15/28.6 ≈ 11%)을 계산해야 원인이 드러납니다.
2. **Elapsed − CPU가 대기 시간**이고, 그 정체는 Row Source의 `pr=`·`time=`로 특정 노드를 지목해 확인합니다.
3. 병목 노드는 `cr`/`pr`이 가장 큰 곳 — 여기서는 회원 Full Scan(cr=738,000, pr=60,000)입니다.
4. 옳은 처방은 병목의 원인(Full Scan I/O)을 줄이는 것이지, 병목이 아닌 자원(CPU)을 늘리는 것이 아닙니다.

📌 한 줄 정리: 수치가 맞아도 병목 지목이 틀리면 오답 — CPU 3.15초는 응답시간의 11%뿐이고 진짜 병목은 회원 Full Scan의 디스크 I/O입니다.
