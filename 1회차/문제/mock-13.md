## 문제 13

### 문제

세 세션이 논리적으로 같은 결과를 얻으려고 아래 SQL을 각각 수행했다. 세 SQL은 **대소문자·공백·주석**만 다르다. 수행 뒤 라이브러리 캐시를 요약한 결과가 함께 주어졌다. 커서 공유(Cursor Sharing)에 대한 설명으로 가장 적절한 것은?

#### [아 래]

```sql
-- 세션 A
select * from orders where cust_id = 100;

-- 세션 B  (SELECT 를 대문자로)
SELECT * from orders where cust_id = 100;

-- 세션 C  (from 앞 공백 2칸 + 끝에 주석)
select *  from orders where cust_id = 100;  -- daily batch
```

```text
[ 라이브러리 캐시 요약 ]
SQL_ID           SQL_TEXT (선두 요약)                          PARSE_CALLS  EXECUTIONS
-------------------------------------------------------------------------------------
9k2m7b3d0x1aq    select * from orders where cust_id = 100            1          1
7f3p5c8e2y6bh    SELECT * from orders where cust_id = 100            1          1
2d5x1a4f9z0ck    select *  from orders where cust_id = 100 --...     1          1
```

### 선택지

① 주석은 실행계획에 영향을 주지 않으므로, 주석만 다른 SQL은 항상 같은 커서를 공유한다.
② 오라클은 파싱 전에 SQL 텍스트를 대문자로 바꾸고 여백·주석을 제거해 정규화하므로, 세 SQL은 하나의 커서를 공유한다.
③ 세 SQL이 동일한 상수값(100)을 사용하므로, 바인드 변수를 쓰지 않아도 커서가 자동으로 공유된다.
④ 세 SQL은 대소문자·공백·주석만 다르고 의미는 같지만, 텍스트가 문자 단위로 일치하지 않아 서로 다른 SQL_ID로 각각 하드파싱되었다.

---

### 정답 — ④

### 왜 ④인가

라이브러리 캐시 요약이 답을 그대로 보여 줍니다. 논리적으로 같은 세 SQL인데 **SQL_ID가 세 개(9k2m…, 7f3p…, 2d5x…)** 로 갈렸고, 각각 `PARSE_CALLS 1 / EXECUTIONS 1`입니다.

```text
9k2m...  ← 세션 A : 원본
7f3p...  ← 세션 B : SELECT 만 대문자
2d5x...  ← 세션 C : from 앞 공백 2칸 + 끝 주석
→ 텍스트가 다르면 SQL_ID가 다르고, 커서를 공유하지 못해 각각 하드파싱
```

오라클의 기본(EXACT) 커서 공유는 **SQL 텍스트를 문자 단위로 비교**합니다. 대소문자·공백·주석 하나만 달라도 다른 텍스트로 간주되어 라이브러리 캐시에서 기존 커서를 찾지 못하고, 새 커서를 만들며 **하드파싱**합니다. 요약표의 세 SQL_ID가 바로 그 결과입니다. ④이 정확합니다.

②는 "옵티마이저가 텍스트를 정규화(대문자화·여백/주석 제거)해 공유한다"는 **정규화 가정의 오류**입니다. 기본 모드에서 오라클은 그런 정규화를 하지 않으므로, 세 SQL은 공유되지 않습니다(요약표가 SQL_ID 3개로 반증).

③은 오히려 반대입니다. **리터럴(상수 100)을 그대로 쓰면** 값이 바뀔 때마다 텍스트가 달라져 커서 공유가 깨집니다. 커서를 공유하려면 상수를 **바인드 변수(:b1)** 로 바꿔 텍스트를 동일하게 만들어야 합니다. "같은 상수라 자동 공유"는 성립하지 않습니다.

①의 주석은 실행계획 결과에는 영향이 없더라도 **SQL 텍스트의 일부**입니다. 세션 C처럼 주석이 붙으면 텍스트가 달라져 SQL_ID가 갈립니다(2d5x…). 따라서 "주석만 달라도 같은 커서 공유"는 틀립니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | 주석은 SQL 텍스트의 일부라 SQL_ID를 바꿉니다. 세션 C의 별도 SQL_ID(2d5x…)가 그 증거입니다 |
| ② | ✗ | 기본 커서 공유는 텍스트를 대문자화·여백/주석 제거로 정규화하지 않습니다. 정규화된다면 SQL_ID가 하나여야 하는데 표에는 셋입니다 |
| ③ | ✗ | 같은 상수를 써도 공유가 자동으로 되는 것이 아닙니다. 오히려 리터럴을 바인드 변수로 바꿔야 텍스트가 같아져 공유됩니다 |
| ④ | **○** | 세 SQL은 의미가 같아도 텍스트가 문자 단위로 다릅니다. 요약표의 SQL_ID가 셋(9k2m·7f3p·2d5x)으로 갈려 각각 하드파싱되었음을 보여 줍니다 |

---

## ✅ 이 문제의 핵심

1. **기본 커서 공유는 텍스트를 문자 단위로 비교**합니다. 대소문자·공백·주석이 하나만 달라도 다른 SQL_ID입니다.
2. **텍스트가 다르면 = 하드파싱.** 요약표의 SQL_ID 개수가 곧 하드파싱한 커서 개수입니다.
3. **리터럴 대신 바인드 변수.** 값이 바뀌어도 텍스트가 같아져 커서를 공유(소프트파싱)할 수 있습니다.
4. 옵티마이저가 텍스트를 정규화해 공유해 준다는 것은 흔한 착각입니다 — 기본 모드에서는 그런 정규화가 없습니다.

📌 한 줄 정리: 오라클 기본 커서 공유는 SQL 텍스트를 문자 단위로 비교하므로 대소문자·공백·주석만 달라도 각각 하드파싱되며, 공유하려면 리터럴을 바인드 변수로 바꿔 텍스트를 동일하게 만들어야 합니다.
