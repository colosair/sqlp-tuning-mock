## 문제 7

### 문제

계약 테이블(약 480만 건)에서 `계약_IX` 인덱스를 경유해 조회한 SQL의 트레이스이다. 아래에 대한 설명으로 가장 적절한 것은?

#### [아 래]

```text
Call       Count  CPU Time  Elapsed Time     Disk     Query   Current      Rows
--------------------------------------------------------------------------------
Parse          1     0.008         0.009        0         0         0         0
Execute        1     0.000         0.000        0         0         0         0
Fetch         33     8.240        41.700    38200    479500         0       480
--------------------------------------------------------------------------------
Total         35     8.248        41.709    38200    479500         0       480

Rows       Row Source Operation
--------------------------------------------------------------------------------
   480     TABLE ACCESS BY INDEX ROWID 계약 (cr=479500 pr=38200
           pw=0 time=41180500 us)
479812     INDEX RANGE SCAN 계약_IX (cr=642 pr=210 pw=0 time=2103400 us)
```

### 선택지

① 인덱스가 넘긴 ROWID 479,812개보다 테이블 액세스의 블록 I/O(cr) 479,500이 더 적으므로, `계약_IX`의 클러스터링 팩터는 매우 좋은 상태다.
② 전체 블록 I/O 479,500 가운데 인덱스 스캔이 cr=642, pr=210을 차지하므로 이 SQL의 주된 병목은 인덱스 스캔 단계이며, `계약_IX`를 재생성해야 한다.
③ CPU Time과 Elapsed Time 간 약 33초 차이는 38,200개 디스크 블록을 읽기 위한 I/O Call 대기 때문일 가능성이 가장 높다.
④ 480행을 Fetch Call 33회로 나눠 반환한 왕복이 Elapsed Time 41.700초의 주된 원인이므로, Array Size를 키우면 해소된다.

---

### 정답 — ③

### 왜 ③인가

트레이스의 **세 숫자**를 먼저 나란히 놓습니다.

```text
479,812  ← 인덱스에서 얻은 ROWID 수 (INDEX RANGE SCAN 의 Rows)
479,500  ← 테이블 액세스 단계의 누적 블록 I/O (TABLE ACCESS 의 cr)
    642  ← 인덱스 스캔에 든 블록 (INDEX RANGE SCAN 의 cr)
```

**클러스터링 팩터**는 인덱스 순서로 테이블을 읽을 때 발생하는 블록 I/O 수입니다. 이론상 최솟값은 테이블 블록 수, 최댓값은 테이블 행 수입니다.

```text
CF ≈ 테이블 블록 I/O ÷ ROWID 수 = 479,500 / 479,812 ≈ 1.0
→ ROWID 하나마다 블록을 거의 한 번씩 새로 읽었다는 뜻
→ CF가 행 수에 육박 = 최악에 가까움
```

즉 ①은 **정반대**입니다. ①이 든 "479,500 < 479,812" 자체는 맞는 비교지만, 그 둘이 거의 같다는 것은 CF가 **최댓값(행 수)에 붙어 있다**는 뜻입니다. 블록 I/O가 ROWID 수보다 작기만 하면 좋다는 것이 아니라, **테이블 블록 수 쪽으로 내려가야** 좋은 CF입니다.

병목이 어디인지는 `cr` 비교로 끝납니다. 인덱스 스캔은 642 블록(pr=210), 테이블 액세스는 479,500 블록 — **전체 블록 I/O의 99.9%가 테이블 액세스**에서 발생합니다. ②가 인용한 642와 210은 박스 그대로지만, 그 값이 곧 "인덱스가 병목"이라는 뜻은 아닙니다. 인덱스를 재생성해 봐야 0.1%를 겨냥하는 것이라 효과가 없습니다(**원인 오귀속**).

이제 시간을 봅니다.

```text
Elapsed 41.7초 − CPU 8.2초 ≈ 33.5초  ← CPU가 아닌 '기다린' 시간
Disk = 38,200 블록  ← 물리적으로 디스크에서 읽어야 했던 블록
```

CPU는 8.2초만 썼는데 실제로는 41.7초가 걸렸습니다. 이 **33초의 간극은 일한 시간이 아니라 대기한 시간**이고, 그 원인으로 가장 유력한 것은 38,200개 디스크 블록을 읽기 위한 `db file` I/O Call 대기입니다. ④가 지목한 Fetch Call 33회는 480행을 Array Size 단위로 나눈 결과일 뿐이고, 그 왕복 비용은 41.700초에 견주면 미미합니다. Array Size를 키워 Fetch를 몇 회로 줄여도 읽어야 할 38,200 블록은 그대로이므로 33초는 남습니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | ✗ | **정반대입니다.** 479,500 < 479,812은 맞지만 두 값이 거의 같다는 것은 CF가 최솟값(테이블 블록 수)이 아니라 최댓값(행 수)에 붙었다는 뜻 — 최악입니다 |
| ② | ✗ | cr=642·pr=210 인용은 맞지만 결론이 틀렸습니다. 642는 전체 479,500의 0.1%뿐이고 나머지 99.9%가 테이블 액세스이므로, 인덱스 재생성은 겨냥점이 어긋납니다 |
| ③ | **○** | CPU 8.2초 대비 Elapsed 41.7초의 33초 간극은 대기 시간이고, 38,200개 디스크 블록 물리 I/O 대기가 가장 유력한 원인입니다 |
| ④ | ✗ | Fetch 33회는 480행을 Array Size로 나눈 결과일 뿐입니다. Array Size를 키워도 읽을 블록 38,200개는 그대로여서 41.700초의 33초 대기는 해소되지 않습니다 |

---

## ✅ 이 문제의 핵심

1. **CF ≈ 테이블 블록 I/O ÷ ROWID 수.** 이 값이 1에 가까우면(=행 수에 육박) 최악, 테이블 블록 수에 가까우면 최선입니다.
2. **병목은 `cr` 비율로 지목**합니다. 인덱스(642) vs 테이블(479,500) — 99.9%가 테이블 액세스입니다.
3. **Elapsed − CPU = 대기 시간.** 이 간극은 대개 물리 I/O(`disk`) 대기이지 Fetch 횟수 탓이 아닙니다.
4. 나쁜 CF의 처방은 인덱스 칼럼 순서 조정이 아니라, 인덱스 커버링(테이블 액세스 제거)이나 테이블 재구성입니다.

📌 한 줄 정리: 테이블 블록 I/O가 ROWID 수와 맞먹으면 CF는 최악이고, 병목은 `cr` 99.9%를 차지하는 테이블 액세스이며, Elapsed와 CPU의 간극은 디스크 I/O 대기입니다.
