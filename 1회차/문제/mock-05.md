## 문제 5

### 문제

배송내역 테이블(약 620만 건)에는 결합 인덱스 `배송_IX = (지점코드, 배송일자)`가 있다. 지점명을 함께 얻기 위해 지점 테이블(기본키 `지점_PK = 지점코드`)과 조인하는 다음 SQL의 실행계획이다.

```sql
SELECT b.배송번호, b.배송일자, b.배송상태, j.지점명
  FROM 배송내역 b, 지점 j
 WHERE b.지점코드 = 'S12'
   AND b.배송일자 >= DATE '2026-06-01'
   AND b.배송일자 <  DATE '2026-07-01'
   AND b.배송상태 = '완료'
   AND j.지점코드 = b.지점코드;
```

이 실행계획에 대한 설명으로 가장 적절한 것은?

#### [아 래]

```text
Id  Pid  Operation                                   ( Cost   Card   Bytes )
---------------------------------------------------------------------------
 0    -  SELECT STATEMENT                            (  285   1850   96200 )
 1    0   NESTED LOOPS                               (  285   1850   96200 )
 2    1    TABLE ACCESS BY INDEX ROWID  배송내역       (  280   1850   64750 )
 3    2     INDEX RANGE SCAN  배송_IX                 (   18   7400         )
 4    1    TABLE ACCESS BY INDEX ROWID  지점           (    1      1      17 )
 5    4     INDEX UNIQUE SCAN  지점_PK                (    0      1         )
```

### 선택지

① 지점코드와 배송일자는 `배송_IX`를 통한 인덱스 액세스 조건으로 처리되고, 인덱스에 없는 배송상태는 TABLE ACCESS BY INDEX ROWID 단계에서 필터로 걸러진다.

② 배송상태 조건도 `배송_IX`의 인덱스 액세스 조건에 포함되어 INDEX RANGE SCAN의 스캔 범위를 좁히는 데 사용된다.

③ 선두 칼럼 지점코드에 `SUBSTR(지점코드,1,2)='S1'`처럼 가공을 가하더라도 `배송_IX`의 INDEX RANGE SCAN은 그대로 유지된다.

④ INDEX RANGE SCAN이 반환한 7,400건이 곧 이 SQL의 최종 결과 건수이며, TABLE ACCESS BY INDEX ROWID 단계에서는 건수 감소가 일어나지 않는다.

---

### 정답 — ①

### 왜 ①인가

플랜의 두 노드에서 나온 **Card 값**을 나란히 놓습니다.

```text
INDEX RANGE SCAN 배송_IX          Card 7,400   ← 인덱스에서 걸러진 건수
TABLE ACCESS BY INDEX ROWID 배송내역 Card 1,850  ← 테이블까지 거친 뒤 남은 건수
```

`배송_IX`는 `(지점코드, 배송일자)` 순서입니다. WHERE에는 `지점코드 = 'S12'`(등치)와 `배송일자` 범위가 있으므로, **선두 칼럼 등치 + 두 번째 칼럼 범위**까지가 인덱스로 훑을 수 있는 연속 구간입니다. 그 결과가 INDEX RANGE SCAN의 7,400건입니다.

배송상태는 인덱스 칼럼이 아닙니다. 따라서 인덱스만으로는 걸러낼 수 없고, ROWID로 테이블 블록을 읽어 온 **TABLE ACCESS BY INDEX ROWID 단계에서 필터**로 처리됩니다. 그래서 7,400건이 이 단계를 거치며 1,850건으로 줄어듭니다.

```text
7,400 (인덱스 액세스: 지점코드=, 배송일자 범위)
  └─ 테이블 필터(배송상태='완료') 적용 → 1,850 (최종)
```

즉 ①이 이 구조를 정확히 서술합니다. 배송상태를 인덱스 액세스로 오해한 ②, 선두 칼럼 가공에도 range scan이 유지된다는 ③, 인덱스 반환 건수를 최종 건수로 본 ④는 모두 이 Card 흐름과 어긋납니다.

### 오답 이유

| 선택지 | 판정 | 이유 |
|:-:|:-:|---|
| ① | **○** | 지점코드(등치)·배송일자(범위)는 인덱스 액세스 조건, 배송상태는 인덱스에 없어 TABLE ACCESS 단계 필터 — Card가 7,400→1,850으로 줄어드는 흐름과 일치합니다 |
| ② | ✗ | 배송상태는 `배송_IX` 구성 칼럼이 아니므로 인덱스 액세스 조건이 될 수 없습니다. 그것이 스캔 범위를 좁혔다면 INDEX RANGE SCAN Card가 이미 1,850이었을 것입니다 |
| ③ | ✗ | 선두 칼럼을 SUBSTR 등으로 가공하면 인덱스 정렬 순서를 탈 수 없어 INDEX RANGE SCAN 자체가 성립하지 않습니다. 경계를 뭉갠 진술입니다 |
| ④ | ✗ | 7,400은 인덱스 단계 Card일 뿐이고, 배송상태 필터를 거친 최종 Card는 1,850입니다. 테이블 액세스 단계에서 건수 감소가 분명히 일어납니다 |

---

## ✅ 이 문제의 핵심

1. **결합 인덱스는 선두 칼럼 등치 + 다음 칼럼 범위까지가 액세스 조건.** 여기서는 지점코드(=)·배송일자(범위)가 INDEX RANGE SCAN 구간을 만듭니다.
2. **인덱스에 없는 칼럼은 테이블 필터.** 배송상태는 ROWID로 테이블을 읽은 뒤 TABLE ACCESS BY INDEX ROWID 단계에서 걸러집니다.
3. **두 노드의 Card 차이(7,400 vs 1,850)가 곧 테이블 필터의 효과**입니다. 인덱스 반환 건수 ≠ 최종 건수.
4. **선두 칼럼을 가공하면 INDEX RANGE SCAN이 깨집니다.** 인덱스 정렬 순서를 그대로 타야 범위 스캔이 성립합니다.

📌 한 줄 정리: 선두 칼럼 등치와 다음 칼럼 범위는 인덱스 액세스 조건이 되고, 인덱스에 없는 칼럼은 테이블 액세스 단계 필터가 되어 Card가 7,400에서 1,850으로 줄어듭니다.
